### 発見済みの落とし穴

1. 抽出から「该」を除くだけでは `materializeGaps` が未網羅文字として単語行を再作成する。文法要素の網羅情報を別途扱う必要がある。
2. 文法の `excerpt` 全域を網羅済みにすると、スロット中の内容語まで消える。「该去学校了」では「该」「了」を文法要素として扱えても「去」「学校」は残す。
3. 現在の文法抽出結果には `excerpt` があるが、保存される `ImportGrammarItem` には同じフィールドがない。正規化→items→保存→再読込の全経路を通す必要がある。
4. 同じ文の同表記語も複数の用法を持つ。`sentenceIndex + term` だけではタップ対象・読み・意味を特定できない。
5. `backfillRepeatedWords` の「同表記なら先頭を参照」は文脈意味を誤継承する。新形式の出現情報には適用しない。
6. スマート追加は意味を渡していても別のLLM定義を末尾へ足すため、言い換えが別語義として残る可能性がある。
7. 現在の解析プロンプトは日本語の説明を返す一方、登録コードは `descriptionLanguage` をラベルに使う。言語設定が違うと日本語に別ISOコードが付く可能性を検証し、生成内容の言語を明記する。
8. 全文を単に「初期状態で開いたモーダル」にすると、閉じると文章別に戻り、ページのスクロールロックも残る。通常の表示モードとして分離する。

## 3. 実装方針（判断を固定する）

### 3.1 全文と文章別の関係

- `ImportReview` に `viewMode: 'fullText' | 'sentences'` を設け、セッションを開くたび `fullText` にする。
- 全文はページ内の通常表示にする。常時開くモーダルにはしない。既存モーダルから読み物部分を取り出して再利用する。
- ヘッダーに「全文」「文章別」を用意し、保存状況・戻る操作を両モードで共通にする。
- 文章別画面の登録・編集機能を維持する。全文の詳細から「この文を文章別で開く」で対象文へ移動できる。
- モード・詳細の開閉・スクロール位置は表示用state。学習データや登録状態には書き込まない。拼音の既存設定キーは維持する。
- モード間では各スクロール位置を保持。記事変更時は詳細選択をリセットし、別記事の説明を表示しない。

### 3.2 タッチの競合をなくす

- 文の背景/句読点など語以外の箇所のタップは文解説を開く。
- 語のタップはその出現の詳細を開き、イベントを親へ伝播させない。
- 全域が語で埋まった文でも文解説を開けるよう、文末に小さい「文の解説」ボタンを必ず置く。
- 語詳細にも「この文の解説」を置く。複数の文法に属する語では関連構文を選べる。
- 非連続構文は固定要素を結びつけて強調する。重複範囲では単一の語ボタン＋関連構文一覧にし、入れ子buttonを作らない。
- 指ドラッグ・長押しで文字を選択した場合は説明を開かない。スクロール終了時の誤タップにも配慮する。
- PCはサイドパネル、狭い画面は下部シートを基本とする。下部シートは適切なdialog、フォーカス制御、Escape、閉じた後のフォーカス復元を実装する。
- 語はキーボードでも選択可能にする。rubyの読みをアクセシブル名へ重複して読み上げさせない。

### 3.3 データは「登録候補」と「文中の出現」を分ける

以下は**新規提案の型/フィールド名**。現行APIにはまだない。実装開始時にfixtureと型を一緒に確定する。

```ts
// 両packageに同じ定義を置く。位置は保存されたsentence.textのUTF-16 index。
type TextRange = { start: number; end: number }; // [start, end)
type ImportOccurrence = {
  id: string;                        // 文内の出現識別子、サーバーで採番
  range: TextRange;
  surface: string;                   // sentence.text.slice(start,end) と完全一致
  lemma?: string;                    // 活用言語用。surfaceとは別
  transliteration?: string;          // この用法の読み
  contextualMeaning: string;
  explanationLanguage: string;       // ISOコード。学習言語名と混ぜない
  partOfSpeech?: string;
  role?: string;
  senseKey?: string;                 // 記事内・解析version内のみ有効。永続Word IDではない
  wordItemId?: string;               // 編集itemsとの関連。無い場合も詳細は読める
  constructionIds: string[];
};
type ImportConstruction = {
  id: string;
  statement: string;                 // 例: 该+v+了
  ranges: TextRange[];               // 非連続構文も扱う
  meaning: string;
  roleInSentence: string;
  elements: {
    occurrenceIds: string[];
    role: string;
    explanation: string;
    fixed: boolean;                  // 内容語スロットか固定要素かを区別
  }[];
  grammarItemId?: string;
};
// ImportSentenceへoptional追加（旧セッション互換）
// readingAnalysis?: {
//   version: number; sourceText: string; explanationLanguage: string;
//   occurrences: ImportOccurrence[]; constructions: ImportConstruction[];
//   overview: string; ambiguityNotes: string[];
// }
```

- `sourceText` が現在の文と一致しない解析は使わず「再解析が必要」と表示する。
- 範囲をLLMの数字だけで信用しない。LLMには原文のsurfaceと出現順も出させ、サーバー側で照合・解決する。曖昧なら無理に先頭へ貼らない。
- `wordItemId`/`grammarItemId` は `buildImportItems` の採番後に結びつける。LLMにアプリIDを作らせない。
- `items` は編集・登録候補の正本。解析には出現の根拠と説明を置き、候補の独立した第二コピーを作らない。
- 有効なリンク先で編集した語の読み/意味は全文でも反映する。ただし同表記の全出現へ無条件に反映しない。
- 分割/結合/削除/undo後はリンクと範囲を再評価する。曖昧になった関連は切り、古い説明を新しい語の説明として見せない。
- 登録から省いた固定要素も `occurrences` に残すため、拼音・意味・文法へのリンクを表示できる。
- `skipped`（ユーザー削除/結合等の履歴）と「文法要素なので独立候補を作らない」を同じ状態にしない。

### 3.4 単語候補を省略する条件

以下をすべて満たす**出現**だけを候補作成対象から外してよい。

1. 文内の範囲が原文と一致する。
2. 検証済み構文の固定要素である（スロット内の語ではない）。
3. 要素単位の読み・文脈意味・役割の説明がある。
4. 同じ語の他の出現に、独立した語彙的用法があればそれは残す。

範囲や役割が不明なら単語候補を残す保守的な動作にする。構文文字列への単純な `includes(term)` で除去しない。登録済み行・手動行・履歴を自動削除しない。

`sentenceCoverage` は「生きた単語候補の範囲 ∪ 有効な固定文法要素の範囲」を扱う。全文の語詳細は候補行の有無に依存させない。文法行を削除した後に、古い関連だけで未説明の文字を網羅済みにしない。派生カバレッジから外し、必要なら既存の手動補完を使えるようにする。

### 3.5 文脈の意味と辞書の語義を分離する

- 全文では「この文での意味」を最優先。一般的な定義一覧は補助表示にする。
- 語義を分ける根拠は、安定した中心義の違い、意味に結びつく構文/項構造の違い、確立した専門義・慣用義。品詞ラベルの差や日本語訳の言い換えだけでは増やさない。
- 「早く」と「速やかに」、対象・丁寧さ・強調の違いなどは原則同一語義。異なる説明文を持つことと異なる語義を持つことは別。
- 「还」hái（まだ）/huán（返す）は区別する。発音の差だけをすべて別義にすることも避ける。
- LLMには語義候補ごとの区別根拠と例を作らせ、根拠のない追加義は既存義へまとめる。説明文の文字列類似度だけで意味を統合しない。
- 新規外部ソース語のsmart-addでは、元文・出現・文脈義を明示した**optionalな文脈入力**を渡す。通常の手動smart-addには必須化しない。
- 元文の用法に対応する定義を必ず含める。近い言い換えを追加定義として末尾へ再追加しない。補足用法はnotes等へ。
- 既存Wordに対するA/B追加は従来どおり所属追加のみ。本文の文脈義は記事側に保持し、既存の辞書定義を自動更新しない。
- 既存全データの語義統合・意味IDの全件導入・例文再紐付けは対象外。必要なら別タスクにする。

### 3.6 解説の表示テンプレート（提案）

文全体は「自然な訳 → 構文ごとの意味とつながり → 各要素の役割」の順で表示する。複雑な文は主節・従属節、修飾先、否定/時制相/モダリティの作用先を示す。単純文でも主語・述語・目的語などを説明できるが、登録候補として平凡なSVOを大量生成しない。

多義要素の詳細は次の順にする。

1. **ここでは**：読み＋今回の意味を一行で。
2. **何をしているか**：品詞/役割、係る語、構文中の位置。
3. **なぜそう読むか**：原文の共起語・語順など具体的な根拠。
4. **混同しやすい用法との差**：関連する一つか二つだけを対比。
5. 必要なときだけ短い比較例。文脈が足りなければ曖昧さを明示する。

解説のfixture候補（言語内容は実装時にレビューして正解データ化）:

- 「他为孩子买了书。」：`为 wèi` は受益者「子供のために」を導く。`孩子` が受益者、`买了书` が行為。`为了` と同じ文字列/構文として処理しない。
- 「他被选为代表。」：`为 wéi` は `选为` の中で選ばれた役割「代表となる」を示す。上の受益者用法と対比する。
- 「我要买书。」：`要 yào` は意図・希望を表す読みが自然。「必须」相当と一律に断定しない。文脈による解釈幅も示す。
- 「要下雨了。」：`要…了` の近い将来/変化を説明。「欲しい」「必要だ」を羅列しない。
- 「该去学校了。」：`该+v+了` 全体で「そろそろ～する時間だ」。`该`、動詞句 `去学校`、`了` の役割を分ける。「去」「学校」の候補は維持できる。
- 「该公司该采取行动了。」：最初の `该` と後の `该` を別出現として扱い、一律に省略しない。

## 8. 読み込みタイムアウトへの対応（2026-10-16）

本番の08:19〜08:29（日本時間）に初回解析が600秒で終了し、ストリーム終端後の通信切断で原因がLoad failedに上書きされる経路を確認したため、初回解析を再設計した。

- 初回は文字数によらずcompact schema。新しい分割解析記事では文を初めて選択した際に詳しい解説を生成して保存する。語の選択・モード切替では呼ばず、旧記事は従来の明示ボタンを維持する。自動生成の失敗は表示し、明示操作で再試行する。
- 元記事を最大300文字の区間に分割し、区間ごとに解析・Firestore transactionで保存。長い文は句読点等を優先して区切り、原文・段落・サロゲートペアを保持する。
- `analysisProgress`を保存し、未完了記事の「続きから解析」で残りだけ処理。時間切れの区間はさらに分割して次の再試行に備える。
- 完了済み区間への再送・同時完了でも候補が増殖しない。既存候補、編集、登録状態、登録先を保持。保存待ちを排出してから再開し、別画面の古いcheckpointによる上書きは409で拒否。
- 通信が最後に切れても保存済みの完了を再取得して復旧。SSE終端エラーをLoad failedで上書きしない。キャッシュされた旧画面が600文字超を旧stream APIへ送る場合は再読込を案内する。
- 文書保存上限は従来どおり。密な大記事は未解析部分を別記事として読み込む案内を表示し、先に保存した内容は保持する。
- 実LLM＋Docker/emulatorで364文字を2区間（280/84文字）に分割し、約107秒/45秒で完了。271候補・13文・約91KBを保存し、再送でも増殖しないことを確認した。
- 今回はDBのprompt/schemaファイルを変更していないため、通常のコードデプロイで反映する。既存データの一括migrationは不要。

この対応の検証結果：backend build・unit 82件、import API回帰6件、mixed quiz回帰4件、frontend型チェック・unit 94件・build、Playwright 16件が成功。実Firestore emulatorでも同一区間を並行して2回commitし、候補は1件だけ、古いcheckpointでのPUTは409となることを確認した。今回の配信結果は作業の最終報告を参照。
