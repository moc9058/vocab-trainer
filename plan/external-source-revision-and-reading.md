# 外部ソースの部分再生成・読解支援・文法から単語への変更

作成日: 2026-10-18
状態: 実装前の計画。機能・API・データ項目の新設案は未実装。

## 1. 目的と範囲

外部ソースのレビュー画面で、次の三つを一貫した操作として提供する。

1. 一文または連続した複数文を選び、指示付きで文法候補・解説を再生成する。
2. 単語や文法の列挙に加えて、文全体の意味、前後との関係、ニュアンスを理解する。
3. 文法候補を単語候補へ変更する、または文法候補を残して単語候補を追加する。

第一段階は文単位の範囲選択、比較・採用・取り消しまでを含む。文法から単語への変更では、一文内の連続した原文範囲の選択も含める。全文リーダーでの自由な文字範囲再生成、複数の離れた範囲の指定、汎用チャット、ライブラリの種別一括変換は後続とする。

この計画作成ではアプリケーションを変更しない。以下の実装工程は別途実施する。

## 2. 現状と利用する基盤

- 全文モードと文モード、文脈上の語義、構文・構成要素表示がある。
- `POST /api/import/:language/sessions/:sessionId/sentences/:sentenceIndex/explanation` は対象文と前後一文から解説を生成する。サーバーは結果を返し、クライアントがセッションへ反映・保存する。登録候補の置換APIではない。
- `ImportReadingAnalysis` は `overview`、`occurrences`、`constructions`、`ambiguityNotes` を持つ。登録・編集用の正本は `ImportItem[]`。
- 原文範囲は UTF-16 の位置で検証される。表記が同じでも出現箇所は区別する。
- 初回解析には永続ジョブ、再開、結果保存、重複要求抑止がある。稼働中は編集・登録を制限している。
- セッション本文は保存容量上限がある。生成履歴をセッション配列に無制限に追加できない。
- A/B登録は既存キューと登録先別の結果を使用する。単語・文法の既存エンティティと候補は別の存在である。

## 3. 画面と操作

### 3.1 範囲指定と再生成

全文・文モードの各文に「選択」を用意する。開始文と終了文で連続範囲を指定し、選択中の原文を強調する。単独文の詳細からも「修正する」を開ける。段落選択は段落内の全文選択として扱う。

修正パネルには次を表示する。

| 項目 | 動作 |
| --- | --- |
| 修正対象 | 選択した原文を省略せず確認できる |
| 更新内容 | 「解説のみ」「文法候補のみ」「文法候補と解説」から選ぶ。既定は文法候補と解説 |
| 修正指示 | 任意の入力欄。前回の指示を再利用・編集できる |
| 指示例 | 「一つの構文としてまとめる」「省略された主語を説明」「この解釈を見直す」 |
| 参照する文脈 | 選択文を含む段落と前後一文。上限を超える場合は対象に近い文を優先し、利用した範囲を表示 |
| 再生成 | 新しい提案を作成。現在の候補はこの時点では変更しない |

対象外の文は解釈の資料としてのみ渡す。モデルに文境界・原文・候補IDの再採番を任せない。選択範囲外へ続く構文は、範囲を広げる提案として表示し、自動更新しない。

提案画面では、原文、現在の内容、新しい内容を比較する。「追加」「変更」「候補から外す」を区別し、採用対象を選んで一度に適用する。要素の参照関係がある解説は文単位で一式採用し、壊れる組み合わせの部分採用を許可しない。

再生成中も原文・既存候補は閲覧可能。第一段階では同一記事の変更操作を直列化し、生成中の編集・登録は無効にする。失敗しても旧内容を残し、同じ要求の状態確認と再試行を提供する。

### 3.2 文全体の読解支援

文の詳細は、次の順で表示する。最初は短い説明を見せ、詳細は展開できるようにする。

1. **この文が言いたいこと**: 自然な日本語による一〜三文の説明。
2. **文の骨格**: 誰が、何を、どうしたか。否定・条件・係り受け・省略を含める。
3. **前後とのつながり**: 理由、対比、結論、具体例、指示語の参照先。
4. **ニュアンス**: 強調、ためらい、婉曲、不満など。根拠となる原文範囲と結びつける。
5. **表現・文法の詳細**: 既存の構文・要素表示。

例: 「他倒是答应了，可一直没行动。」では「承諾はしてくれたものの、実際にはずっと何もしていない。承諾と行動の食い違いを指摘している」を先に示し、その後で倒是・可などとの関係を説明する。

明示されている意味、文脈からの推測、判断不能を区別する。省略主語・話者の意図を断定しない。複数解釈が成立する場合は主な候補と、判別に足りない文脈を表示する。

「もっと簡単に」「なぜこの意味になる？」「直訳との違い」「前の文との関係」と自由入力を再生成指示として利用する。対象範囲に紐づく直近の採用済み指示を保存し、再編集できるようにする。UI言語と説明言語は別フィールドとし、初期値は現状の日本語説明を維持する。

### 3.3 文法から単語への変更

文法カードと構文詳細に「単語として扱う」を追加する。全文モードでも文モードでも同じダイアログを使う。

1. 原文と該当する構文範囲を表示する。
2. 登録したい連続する語句を選ぶ。同表記の複数出現は位置で区別する。
3. 単語の見出し・読み・この文での意味・説明言語を確認する。活用形の言語では原文表記と見出し語を別に保持する。
4. 「単語に変更」または「単語としても追加」を選ぶ。
5. 候補として保存し、既存のA/B登録操作へ進める。

`对＋対象＋来说` のようなパターンを、そのまま単語名にしない。非連続構文では一つの連続した語句を選び、複数の単語が必要なら追加を繰り返す。

読み・意味は既存の対応する語情報から補える場合のみ引き継ぐ。文法全体の説明を無条件で語義へコピーしない。任意の「意味・読みを整える」でLLMを呼び、確認後に採用する。手動入力だけでも保存できる。

既存単語候補が同じ出現位置にある場合は、その候補を開くか修正する。既存ライブラリに同じ語がある場合は、既存の照合・再利用フローを使い、辞書定義を上書きしない。

| 元候補の状態 | 「単語に変更」の結果 |
| --- | --- |
| 未登録 | 元文法候補を記事内で非表示にし、単語候補を作る。履歴から復元可能 |
| 登録済み・既存文法への参照あり | 文法エンティティとA/B所属は維持。記事内の元候補を非表示にし、独立した単語候補を作る。残る登録を画面で明示 |
| 登録処理中・未保存 | 完了または保存を待つ。操作途中の候補は変換しない |

「単語としても追加」は元候補を表示したままにする。新しい単語に文法のエンティティID・登録結果・学習履歴をコピーしない。構文解説も残す。必要なライブラリ削除・所属解除は既存の別操作で行い、変換の副作用にしない。

## 4. データ設計案

### 4.1 原文・解説・候補の分離

- 原文と文境界は修正機能で変更しない。
- `ImportReadingAnalysis` を後方互換で拡張し、全体の意味、骨格、文脈関係、根拠付きニュアンス、解釈の確実性を構造化する。旧 `overview` は表示フォールバックとして残す。
- 原文の範囲は `{ sentenceIndex, start, end, sourceTextHash }` で照合する。インデックスのみで適用しない。
- 候補IDは維持・追加・除外を明示し、モデルが返した順番やstatement一致だけで既存候補を置き換えない。対応が曖昧なら追加候補として比較させる。
- 候補に由来情報（元候補ID、修正操作ID、原文範囲）と記事内の表示状態を追加する。非表示化しても登録先別の結果を失わない。
- 単語へ変更した事実を保存し、gap補完・重複整理・解説の再照合で元文法候補が復活しないようにする。

### 4.2 提案・履歴

提案用のサブコレクション `import_sessions/{sessionId}/revisions/{revisionId}` を新設する案とする。

保存内容: 操作種別、対象範囲、指示、期待するセッション版、生成状態、生成結果、候補差分、採用内容、適用前後の対象部分、作成日時、冪等キー。状態は `queued / running / proposed / applied / rejected / failed / undone`。

セッション本体には現在の表示・候補と版番号だけを保持し、履歴全体を埋め込まない。各文書のバイト上限を検証し、長い範囲の結果は文別の結果文書に分ける。適用後のセッションが既存900,000バイト上限を超える場合は、旧内容を維持して範囲縮小を案内する。

未採用・失敗の生成ペイロードは7日を初期保持期間とする。採用済み履歴は記事ごと直近20操作まで保持し、UIで取り消し可能範囲を示す。セッション削除時は提案・履歴・結果も削除対象にする。

### 4.3 取り消しと登録

取り消しは記事内の変更だけを対象とする。後から行われた登録・進捗・グループ所属を逆操作しない。単語登録後の取り消しでも登録済み単語は残ることを表示する。

まず最新の採用操作を取り消す機能を提供する。対象が後続の編集・登録によって変わっている場合は、丸ごと巻き戻さず競合を返し、旧内容を新しい復元提案として比較できるようにする。

記事クイズpoolは既存登録を勝手に落とさない。非表示候補の登録記録も従来の登録済みIDとして扱い、単語変換による文法所属解除は行わない。進行中クイズは変更せず、既存の開始・再開処理を維持する。

## 5. API・バックエンド案

以下は新設案。共通prefixは `/api/import/:language/sessions/:sessionId`。

| メソッド・パス | 用途 |
| --- | --- |
| `POST /revisions` | 範囲・更新内容・指示・expectedRevision・idempotencyKeyを受け、202で生成要求を受理 |
| `GET /revisions/:revisionId` | 状態・生成提案・失敗理由を取得 |
| `POST /revisions/:revisionId/apply` | 選択した差分を版検証付きで原子的に適用 |
| `POST /revisions/:revisionId/reject` | 提案を不採用にする |
| `POST /revisions/:revisionId/undo` | 適用済み操作の取り消し、または競合を返す |
| `POST /candidate-conversions` | 手動の文法→単語変更・追加を適用し、同じ履歴形式に記録 |

LLMを利用する単語補助生成も `POST /revisions` の操作種別で処理する。手動変更ではLLMを呼ばない。

生成は初回解析のジョブ基盤のlease、結果保存、重複要求抑止、再開機構を再利用する。ただし既存の初回解析checkpointを流用して上書きしない。修正ジョブには独立した操作IDと結果保存先を持たせる。受付API内でLLM完了を待たない。

適用時はサーバーで原文・対象候補・版番号・参照整合性・容量を検証する。旧応答や同時編集は409、存在しない記事は404として区別する。原子的な適用と同じ要求の再送による二重追加防止を行う。

既存 `analysisRevision` の意味は初回解析制御として保ち、全編集用の `contentRevision` を追加する案とする。通常の手動編集、解説保存、登録結果保存、修正適用も同じ版検証に参加させる。既存PUTが新しい変更を上書きできるままにはしない。旧記事は欠落版を0として最初の書き込みで付与し、一括migrationはしない。

クライアントは修正開始前に未保存編集と登録キューを排出する。版競合時はユーザー入力を保持して最新状態を取得し、比較・再適用できるようにする。データ保存先はFirestoreとし、localStorageには表示設定だけを置く。

プロンプトは根拠のない意図の断定を避け、参照文脈と更新対象を明確に分離する。生成した原文書き換え・不正範囲・不完全JSONは採用しない。モデル呼び出しの使用量記録は既存方式を利用し、結果保存前の障害による再課金を完全に防げるとは表示しない。

## 7. 検証と受け入れ条件

- 選択外の文・候補・手動編集が変わらない。原文と文境界は全操作で同一。
- 同じ語の反復、非連続構文、中国語の多音字、日韓の活用、英語の句動詞を扱える。
- 解説のみの更新では候補と登録結果が変わらない。
- 文法→単語で新しい候補IDを持ち、文法の登録済み表示を引き継がない。
- 「追加」は元文法候補を残し、「変更」は候補のみを非表示化する。共有文法・例文・所属・進捗を削除しない。
- 固定文法要素由来の単語も明示変換後は表示され、dedup/gap補完で消えたり元候補が復活したりしない。
- 採用しない提案、LLM失敗、容量超過、不正な範囲でも既存内容を維持する。
- 二重クリック、受付応答喪失、ページ再読込、worker再実行で生成ジョブ・候補・適用が重複しない。
- 別タブの保存・登録結果・初回解析再開と競合した古い提案を適用しない。
- 再読込後も指示、採用済み内容、履歴、登録結果が一致する。
- 360px画面、キーボードによる範囲選択、フォーカス復帰、スクリーンリーダーの状態通知を確認する。
- 実LLMの少数例で「文法の列挙だけになっていない」「ニュアンスに根拠がある」「不明点を断定しない」を人が確認する。構造テストだけで意味品質を合格にしない。

実装時に行うチェック（Node 24）:

```bash
npm run build --prefix backend
npm test --prefix backend
npm run test:import --prefix backend
npm run test:mixed --prefix backend
(cd frontend && npx tsc --noEmit)
npm test --prefix frontend
npm run build --prefix frontend
npm run test:browser --prefix frontend
npm run test:import:emulator --prefix backend
git diff --check
```

エミュレーター用のテストには稼働中のFirestore emulatorが必要。`./local.sh`の手順でローカル環境を起動し、Dockerと実LLMを使う少数例のスモークテストも行う。利用できない検証は未実施として報告する。本番データを試験用に変更しない。

## 8. 配信と後続範囲

実装完成時はREADME・開発リファレンスを更新し、過去の監査記録は書き換えない。プロンプト・schemaの変更を含む配信では `./deploy.sh --prompts`、コードのみの場合は `./deploy.sh` を利用する。新機能のプロンプト配信は本計画ファイル作成時には行わない。

既存記事は従来表示のまま読め、明示的な修正操作時に拡張データを生成する。本番の一括再解析や登録済み辞書の一括書き換えは不要。

後続では自由な文字範囲の再生成、非連続範囲選択、複数単語への一括分割を検討する。まず上記の一文・複数文で、理解と修正が完結することを優先する。
