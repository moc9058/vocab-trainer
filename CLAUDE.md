### Deploy
```bash
./deploy.sh PROJECT_ID REGION            # Deploy only
./deploy.sh PROJECT_ID REGION --llm      # Deploy + upload LLM config to config/llm
./deploy.sh PROJECT_ID REGION --auth     # Deploy + upload Google OAuth config to config/auth
./deploy.sh PROJECT_ID REGION --prompts  # Deploy + upload prompts/schemas from backend/DB/
./deploy.sh PROJECT_ID REGION --no-prune # Deploy WITHOUT the post-deploy cleanup below
# Windows: .\deploy.ps1 PROJECT_ID REGION [-Llm] [-Auth] [-Prompts] [-NoPrune] — same four.
```
The deploy scripts carry exactly two things: **config uploads** and the
**post-deploy retention** described below. The uploads belong here only because
config is read once and memoized for the process lifetime (`routes/import.ts`) or at
boot (`auth-config.ts`) — so pushing it and rolling a revision are one operation. Data
migrations (`migrate-example-sentences.ts`, `migrate-grammar-examples.ts`,
`--archives`) and destructive maintenance (`wipe-grammar-firestore.ts`) used to be
deploy flags and are now run directly; they have no relationship to a release, and
a wipe reachable from the deploy command is one someone eventually runs by reflex.
`migrate-to-firestore.ts` (the old word import) reads `backend/DB/word/`, which is
empty — nothing is uploaded from the local repo any more. An unknown flag is
rejected rather than silently taken as `PROJECT_ID`.

`--llm` still uploads only the three `config/llm` keys (API key + the two tier
defaults). **Per-feature model assignment is not a deploy concern**: it lives in
`config/llm_models`, is written by the in-app LLM Models screen, and takes effect
within 30 seconds without a new revision. That separation is also what stops
`--llm`'s full `.set()` from wiping it.

#### Post-deploy retention (`--no-prune` / `-NoPrune` opts out)
Every deploy ends by deleting what the previous one superseded — local `<none>`
image, Artifact Registry versions past `KEEP_IMAGES` (5), Cloud Run revisions past
`KEEP_REVISIONS` (5), build cache past `BUILD_CACHE_LIMIT` (10GB); all four are
overridable (env vars in bash, parameters in PowerShell). It exists because nothing
here was ever collected: the repo reached **53 local images, 31GB of build cache,
54 registry versions and 888 inactive Cloud Run revisions** (of a 1000-per-service
cap) before this was added. Pruning runs **after both services are up**, since the
counts assume the newest image and revision are the ones now serving.

Two traps the prune code is written around, both of which delete production if you
get them wrong:
- **Never pass `--limit` to `gcloud artifacts docker images list`.** It is applied
  server-side *before* `--sort-by`, so you get an unsorted page and delete whatever
  landed on it.
- **Never "delete everything untagged".** With buildx provenance ON, one push writes
  **three** versions — an OCI index (which holds the tag) plus an amd64 child and an
  attestation child, *both untagged* — and **Cloud Run pins the child digest**, so an
  untagged-sweep deletes the running image. Both builds therefore pass
  **`--provenance=false`**, which collapses a push to a single tagged manifest and is
  what makes plain count-based retention correct. **Both halves are measured, on
  2026-08-04**: the three pushes before the flag was committed each wrote index + amd64
  child + attestation child, and the first push after it wrote exactly **one** tagged
  version. (The containerd image store is active here and does *not* force an index for
  a single `--platform`.) Re-check the same way if the builder ever changes — one push
  shares one `createTime`, so `gcloud artifacts docker images list … --sort-by=~createTime`
  shows the group size directly. Versions pushed BEFORE the flag are still
  index-shaped, and count-based retention can split such a group: `--delete-tags` on a
  child an index still references fails, the script swallows it as
  `skipped (still referenced)`, and the group survives whole. That is why the repos sat
  at 10 and 9 versions against `KEEP_IMAGES=5` right after the first pruning deploy —
  the leftovers are legacy three-version groups, not a bug in the retention count, and
  they clear once the newest 5 are all single-manifest pushes.

Rollback is by revision (`gcloud run services update-traffic --to-revisions=REV=100`),
which works only while the digest that revision pins still exists — that is why
`KEEP_IMAGES` and `KEEP_REVISIONS` are kept in step.

#### Automatic vulnerability scanning is OFF, deliberately
`containerscanning.googleapis.com` is **disabled** on `vocab-trainer-490014` (as of
2026-08-04). Artifact Analysis bills **$0.26 per newly-pushed digest**, and this repo
deploys often — 73 `deploy.sh` runs in the preceding 30 days, each pushing both images
— while **two of the three manifests per push were being scanned separately**
(the OCI index and the amd64 child each get their own `DISCOVERY` occurrence; the
attestation child gets none). That measured **259 scans / ~$67 in 30 days**, and 1,471
scans / ~$382 since the project began in March — for findings nothing consumes: there
is no Binary Authorization, no Security Command Center and no gate in `deploy.sh`.
Pruning does not help, since the charge lands at push time and a later delete refunds
nothing. Verified silent after the fact: the 12:16 deploy that day produced **zero**
new `DISCOVERY` occurrences. Re-enable with
`gcloud services enable containerscanning.googleapis.com`, or scan deliberately with
`gcloud artifacts docker images scan` (same price, only when asked) — note that
`--provenance=false` now makes a push ONE digest rather than three, so re-enabling
would cost about half what it used to at the same deploy cadence, not the full $67. `containeranalysis.googleapis.com` stays enabled — it is metadata storage and
bills nothing on its own. To audit the real spend, count scans rather than trusting an
estimate: each billed scan is exactly one `DISCOVERY` occurrence, listable from
`https://containeranalysis.googleapis.com/v1/projects/<id>/occurrences?filter=kind="DISCOVERY"`.

## Architecture

Full-stack vocabulary quiz app supporting four study languages (`en`/`ja`/`ko`/`zh`; HSK levels apply only to Chinese): **Fastify 5 backend** + **React 19 / Vite 6 frontend**.

### Authentication (Google OAuth)
Single-user access gating, NOT multi-tenancy — there is no `users` collection and no `userId`/`ownerId` on any document, so every signed-in user shares one dataset. Access is an email allowlist.

- **`auth-config.ts`** — resolves config once, **eagerly at boot** (unlike `llm.ts:loadLLMConfig`, which is lazy) because the request hook must know the posture before serving anything. Env vars win, else Firestore `config/auth`. Three outcomes, and the distinction is the whole security posture: env complete → auth on; **`config/auth` missing → auth OFF** with a loud warning (this is what lets the code deploy before the OAuth client exists); **Firestore read threw → `process.exit(1)`**. Never guess "off" from an error — that would reopen the public API on a transient blip. Also owns the stateless session token (`signSession`/`verifySession`) and the PKCE/state envelope (`signTransaction`/`verifyTransaction`), both HMAC-SHA256 over a base64url JSON body. Sessions are **stateless by necessity**: Cloud Run scales past the one warm instance and an in-memory store would drop them.
- **`routes/auth.ts`** (`/api/auth`) — `GET /login` (302 to Google, `state` + PKCE in a 10-min cookie), `GET /callback` (state check → token exchange → ID-token claim validation → allowlist → session cookie → 302 to the SPA; failures redirect to `/?auth_error=<reason>`, `forbidden` being the not-on-allowlist case), `GET /me` (**public**; returns `{authEnabled, authenticated, user}` — 200 with `authenticated:false` when logged out, never 401, since this is how the SPA discovers its own state), `POST /logout`. **No `google-auth-library`**: the ID token arrives over TLS straight from Google's token endpoint, which is the documented case for skipping JWKS verification, so claims (`aud`/`iss`/`exp`/`email_verified`) are checked directly.
- **`index.ts`** — the codebase's **first and only `onRequest` hook** (there were zero `addHook`/`preHandler`/`decorate` calls before). No-ops when auth is disabled, lets `/api/auth/*` through, else 401. The allowlist is re-checked **per request**, not just at sign-in, so removing an address revokes live sessions. CORS is no longer a bare `register(cors)` — it is an origin allowlist with `credentials: true`; `ALLOWED_ORIGINS` overrides the built-in list.
- **Cookies**: `vt_session` (30d) and `vt_oauth_tx` (10min), both `HttpOnly; SameSite=Lax; Path=/`. **Lax, not Strict** — Strict would drop the cookie on the top-level redirect back from Google. `Secure` is derived from `OAUTH_REDIRECT_URI` being `https://` so local dev over http still works.
- **The redirect URI points at the FRONTEND origin** (`https://<frontend>/api/auth/callback`), not the backend: nginx reverse-proxies `/api/` so the callback still runs in Fastify while the browser stays on the SPA origin, which keeps the session cookie first-party.
- **`OAUTH_REDIRECT_URI` is a COMMA-SEPARATED LIST, one entry per hostname the app answers on** — Cloud Run serves this service at both `…-olncevthqa-an.a.run.app` and `…-839843597381.asia-northeast1.run.app`, and `vt_oauth_tx` is origin-scoped, so starting the flow on one host and being returned to the other loses the cookie and fails the state check with `auth_error=state_mismatch`. `routes/auth.ts:resolveRedirectUri` picks the entry matching the incoming host (unknown host → `[0]`, the canonical one), and the chosen URI is carried **inside the signed transaction** because the token exchange must replay it byte-identically. Every entry must also be registered on the OAuth client in the Console.
- **`nginx.conf.template` must set `X-Forwarded-Host $host`** — it also sets `Host $proxy_host`, which rewrites Host to the backend hostname, so that header is the only surviving record of the public host. Removing it silently breaks multi-host sign-in. The backend never infers the URI from `Host`.
- **Config changes need a restart**, since it is read at boot: `./deploy.sh … --auth` migrates *and* rolls a new revision, which is why they are one flag.
- Both Cloud Run services stay `--allow-unauthenticated`; the app-level hook is the only thing protecting the directly-reachable backend URL.

### Backend (`backend/src/`)
- **Routes** (each is a `FastifyPluginAsync` registered under `/api`):
  - `routes/auth.ts` — see the Authentication section above.
  - `routes/vocab.ts` — smart-add always asks LLM for all four codes (`en`/`ja`/`ko`/`zh`) — `ALL_DEFINITION_LANGUAGES` is hardcoded (lives in `exampleTranslations.ts` with `LANGUAGE_TO_ISO`); request body languages are anchors only. **Before storing, the word's OWN language code is deleted from both `definitions[].text` and every example `translation`** (a same-language gloss is redundant), so a Chinese word persists `en`/`ja`/`ko` only — four are requested, three are saved. Words added before `b7e81ac` (2026-04-08) predate that strip and still carry the source-language definition, so the corpus is mixed. Empty example translations (chip adds send `""`) are normalized to `null` before the LLM call, and any example doc still empty after the merge is LLM-filled via `exampleTranslations.ts:generateMissingExampleTranslations` — shared by vocab POST/PUT and grammar's `resolveExamplesToIds`. Chinese levels normalized at storage time by `CHINESE_LEVEL_NORMALIZE`. Word-group ordering is persisted through `PUT /api/vocab/:language/groups/order`, whose `groupIds` body must contain every group for that language exactly once — and that order is the **priority** (see `word_groups` below). `POST /api/vocab/:language/groups/normalize` re-files a whole language by that priority (`{dryRun?, expectedGroupIds?}`; `dryRun` previews, `expectedGroupIds` is a precondition that 409s if another tab reordered since the preview — it is NOT a second reorder path). **Word drafts**: `word_drafts` Firestore collection + CRUD under `/api/vocab/:language/drafts` (bulk POST assigns `id`/`createdAt` server-side; NO LLM at upload) — mirrors `grammar_drafts`. `WordList`'s "Upload JSON" button ingests `word-drafts` files (format: `docs/draft-json-format.md`). Draft examples may carry `segments: string[]` (chip segmentation — plain segment texts, NOT the `Example.segments` object shape); the review prefill re-inserts spaces at those boundaries (`spaceSentenceBySplits`) so the Chinese chip workflow picks them up and `buildPayload` re-emits them as smart-add `userSplits`. Review flow (mirrors grammar): drafts panel in `WordList` → `SmartAddWordModal` opens with `initialItem`/`initialGroups`/`draftId` prefill and TWO actions — "Save Draft" (form submit / Enter; `onDraftSave` → `PUT /drafts/:draftId`, writes edits back WITHOUT promoting) and an explicit "Register" button that ENQUEUES into the shared word queue (`enqueue` opts `{groupNames, draftId}`: worker creates missing draft groups under the module-level group lock and deletes the draft only after full success — a failed registration keeps the draft) and closes the modal immediately. In-flight drafts show a "Registering…" badge (via `pendingDraftIds`, threaded Dashboard → BrowseView → WordList) with Review/Discard hidden. **Drafts carry NO group data** (removed from the JSON format and both draft types): the drafts panel header has a group `<select>` — defaulting to the highest-PRIORITY group (`types.ts:defaultWordGroup`, i.e. `categoryGroups(groups,"A")[0]`; a user pick sticks until the language changes) — that supplies the target for both the per-row one-click "Register" button (`handleRegisterDraft` builds the smart-add payload straight from the draft, Chinese `segments` → `userSplits`, and enqueues with `{draftId}` so the queue deletes the draft only on full success) and the review modal's preselected group chip (`initialGroups`). A legacy `groups` field in an uploaded file or a direct POST is dropped. Fallback without `onQueue`: direct smart-add await where `onSave` (success-only) is the delete-draft signal.
  - `routes/quiz.ts` — `POST /start` accepts `groupWeights?: Record<string,number>` and `flaggedOnly?: boolean`. When `groupIds` are provided, questions are ordered by `weightedInterleave` (proportional to per-group weights, default 1) instead of `randomSample`; `randomSample` is still used for ungrouped sessions. Resume re-applies weights via `reweightUnanswered` (not a plain shuffle). `PUT /session/language/:language/weights` changes `groupWeights` MID-SESSION: it reorders the unanswered tail with the new weights and returns the full session (questions are SLIM — `slimQuestions` is all Firestore holds) — `QuizTaking`'s "⚖ Adjust Weights" panel re-syncs its local order from the response and jumps to the first unanswered question; the payloads come from its own cache, so a reorder costs no network. **Hydration is BY ID, not by session position** (`POST /hydrate/:language`, body `{wordIds}` → `{questions}`): a session's order changes constantly (retry re-queues, resume reweighting, weight edits) while the SET of ids never does, so an id-keyed client cache makes every reorder free. The endpoint needs no session, so the word, Group A and Group B quizzes all share it — there is no per-quiz `/questions/:language` any more, and no `BATCH_SIZE` paging. `POST /start` still returns lightweight `{wordId, term}`. Wrong answers call `insertRetryQuestion` server-side, which splices the missed word into the tail — `score.total` grows accordingly; the client applies the same mutation locally (see the offline section under **Frontend**) and does not wait for the response.
  - `routes/grammar.ts` — `Grammar` has `statement` + `descriptions: Meaning[]` (mirrors `Word.definitions`). Examples are normalized into the shared `example_sentences` collection via `exampleIds[]` (mirrors `Word.exampleIds`); inline `Grammar.examples` is a transitional fallback for unmigrated docs. POST/smart-add/PUT resolve incoming `examples` to existing or new `example_sentences` docs via the sha256 dedup index (so a sentence shared with a vocab word gets one doc) and `addGrammar`/`updateGrammar` keep `ExampleSentence.appearsInGrammarIds` in lockstep using a Firestore batch. PUT delete-cascades dropped examples through `isExampleReferencedByAny` (cross-domain check covering both `Word.appearsInIds` and other `Grammar.exampleIds`). User-curated `grammar_groups` collection mirrors `word_groups` — per-language, owns membership via `grammarIds[]`. CRUD lives under `/api/grammar/:language/groups`. `POST /:language/smart-add` LLM-enriches `descriptions[].text` to all four ISO codes (mirrors vocab smart-add); `GrammarFormModal` create path uses smart-add, edit (PUT) stays manual. **`Grammar.transliteration` (statement pinyin) is generated for Chinese at EVERY write path** — the local `resolveTransliteration` helper is called from `POST /items`, `POST /smart-add` and `PUT /items/:id` alike (in parallel with `resolveExamplesToIds` on the two creates), so "a stored Chinese grammar item has a reading" holds no matter which route the caller used. It exists because only `GrammarFormModal` ever had an INPUT for the field, so every queue-driven create (article import above all, which is what feeds Group B) stored Chinese grammar with no reading and the quiz reveal had nothing to show. The helper NEVER overwrites: a supplied or already-stored value is returned untouched, which is what makes it safe on PUT — an edit fills a missing reading but cannot clobber a hand-tuned one (`undefined` is dropped by `ignoreUndefinedProperties`, leaving the stored value alone). A failure logs and stores without it rather than sinking the write.

`llm.ts:fillGrammarTransliteration` does the work, and its alignment guarantee is **structural, not prompted**. A statement is pattern notation, so `splitStatementForReading` (exported, pure) cuts it in code into maximal CJK / non-CJK runs; only PURE-HAN runs are sent to the model (a run holding any kana is Japanese annotation — 「状態を表す述語」 — and is kept verbatim), and the result is reassembled here. Placeholders, connectors and spacing therefore never reach the model and cannot be dropped: the earlier whole-string prompt silently ate the leading `s+` of 「s+使役動詞+人/もの+v」 and truncated 「s+被/让/叫+行為者+v+結果補語」 to just "bèi/ràng/jiào". A term that merely *contains* digits or symbols beside letters (「09988.HK/NYSE」, "24/7") is legitimate and kept. Decisions run in two passes so a correctly-filed row is never displaced by a misfiled one that happened to come first in the array. Existing grammar `statement`s are injected as style examples. **The analysis is EXHAUSTIVE, not selective**: `backend/DB/import/system_prompt_analyze_*.md` ask for complete per-sentence segmentation — every letter/ideograph of a sentence must belong to exactly one `words` entry (function words, particles and measure words included; only punctuation, spaces and digits are left out), listed in sentence order, once per sentence per distinct term but AGAIN for every sentence the term appears in, since each sentence has to be covered on its own. `term` is the SURFACE form (a verbatim substring of the sentence) so the client can match it back positionally — this is why the prompts no longer ask for the dictionary form. **That substring requirement is a hard contract with `utils/importSession.ts:termOccurrences`, and each prompt spells out its own language's way of breaking it**: a `term` that is not found verbatim is either repaired server-side (zh/en, above) or — in Japanese and Korean — falls to the longest-prefix fallback, which sets `SentenceCoverage.approximate` and so makes `materializeGaps` refuse to turn that sentence's gaps into rows. Hence English forbids a multi-word entry whose words the sentence separates ("gave it up" → three entries, never "give up") and requires contractions/possessives to stay whole ("don't", "company's" — a bare "n't"/"'s" can never satisfy `boundedAt`'s word-boundary test), while Chinese requires 离合词 to follow the surface (「见了面」 → 见/了/面, never 见面). The Latin-only rules in `termOccurrences` (word boundaries, case-insensitivity) apply to SINGLE words only, which is why the English prompt also pins capitalization for multi-word entries. Chinese additionally pins pinyin to CITATION tones (一 "yī", 不 "bù", 「你好」 "nǐ hǎo") because `transliteration` becomes a library-wide dictionary reading, not a per-sentence one. **`transliteration`/`meaning` are written ONCE per term, on its first occurrence in the article; every later occurrence returns `""` for both** and `import-analysis.ts:backfillRepeatedWords` (exported, unit-tested) fills them in — it runs AFTER the attribution repair, so a dropped bogus row can never be the occurrence everything else inherits from — FIRST wins, not last, and the two fields inherit independently, since the model routinely blanks one and not the other. The prompts carve out an explicit exception for a genuinely different reading or sense (多音字 还 hái/huán, 了 le/liǎo; Japanese 行った itta/okonatta; English "lead"/"read"), which must still be spelled out — without it polyphony would collapse onto the first reading.   **The mixed A+B quiz** (`/api/mixed-quiz`, UI "Group A+B ミックスクイズ", **Chinese only** — gated by `showMixed = isoCode === "zh"` in `EmptyState.tsx`; it is now the file's ONLY language gate, the English-hides-grammar one having been removed) exists because Group B is by definition a SUBSET of Group A, so neither existing quiz could express "drill this week's lesson with my weak words mixed in thicker". Three client-side mechanisms carry it, all in `frontend/src/utils/quizGroupScope.ts` (pure, mirrors the `utils/weightInput.ts` split):
  - **`scopedGroups(groups, "AB")` lists category B FIRST**, and that order is load-bearing rather than cosmetic. `getFilteredWords` unions the selected groups' `wordIds` so the pool has no duplicates, and `assignMembership` gives each item to the FIRST group in `groupIds` order that holds it — so B-first is precisely what makes a word sitting in both an A lesson and a B study set count against B's weight. Consequently `buildFilters` emits `groupIds` in **list order, not Set-iteration order**: unchecking and rechecking a group moved it to the end of the `Set` and silently broke the B-first rule.
  - **`applyCategoryRatio` folds the A↔B ratio into the per-group weights**, because the backend weights buckets per GROUP, not per category. Scaling each side by the OTHER side's weight-sum (`a_i * wA * S_B` vs `b_j * wB * S_A`) lands on the requested ratio **without dividing**, so integer inputs stay integers for `scaleWeightRecord` to GCD-reduce. A category with nothing selected scales by 1, not 0, which would otherwise zero the whole domain. This is worth a helper because the correct per-group number is not one a user would guess: five A groups against one B group at 1:3 gives the B group weight **15**, and it changes every time a checkbox is ticked.
  - **`categoryDomainWeights` + `foldMixWeights` give each category its OWN word:grammar ratio**, which is the whole point of the quiz — "Group B grammar-heavy, Group A vocabulary-heavy" is not expressible with one global domain pair. The user's six numbers (A:B, then word:grammar inside A and inside B) fold onto the backend's existing two knobs and **no handler changed**: `domainWeights[k] = p.A[k] + p.B[k]`, and the per-group weights carry `p.A[k] : p.B[k]` through `applyCategoryRatio`. It lands exactly because the backend draws in TWO stages that multiply — `share(A,word) = (pAw+pBw)/T × pAw/(pAw+pBw) = pAw/T`. Each category's pair is scaled by the OTHER's pair-sum (the same no-division trick one level up), so `A:B = 2:1` with A at `3:1` and B at `1:2` gives `p = 18, 6, 4, 8` → `domainWeights {word:22, grammar:14}`, word groups A:B = 9:2, grammar groups A:B = 3:4. A category contributes to a domain **only when it has a group selected there**, or `p.B.grammar` would inflate the grammar bucket with nothing to draw. `roundWeight` clamps every product to 6 decimals: a fold multiplies up to four user numbers, and raw float noise (`0.1*3`) would make `decimalPlaces` scale by 1e17 and overflow `Number.MAX_SAFE_INTEGER`.
  - **`CombinedQuizSession.mixWeights` stores the UNFOLDED six numbers** (`MixWeightConfig`, mirrored in both `types.ts`), accepted by `POST /start` and `PUT …/weights` and echoed back. The server never reads it — ordering uses only the folded values — but **the fold cannot be inverted** (a category's share is smeared across its groups' weights), so without it the mid-session ⚖ panel could not show back what the user typed. Adding it needed a line in `firestore.ts:getCombinedQuizSession`, whose field list is a **whitelist**: an unlisted session field is silently dropped on every read. `PUT` replaces it wholesale rather than merging like `wordGroupWeights`, since it is one coherent set of ratios, not a per-group patch. Absent on every other variant and on mixed sessions predating it — which is exactly the signal `CombinedQuizTaking` uses to fall back to the flat editor.

Its own `expression_recall_sessions` collection (doc id = language), a real sub-path `/:language/expression-recall`, and the same shape as `routes/grammar-quiz.ts`: without an explicit `questionCount` the session covers the **entire** matching pool (weights decide ORDER, never who makes the cut), ordering is `weightedInterleave` when `groupIds` are given and `shuffle` otherwise, resume re-draws the unanswered tail, and **retries are appended, not spliced** (matching grammar; `utils/quizLocal.ts` mirrors whichever applies). `direction` (`"phrase-to-context"` default, or `"context-to-phrase"`) picks which face is the prompt and is stored on the SESSION; the prompt text is **denormalized onto each question** so a card renders before hydration lands — which also means a mixed-direction mode isn't representable, and editing an expression mid-session leaves the stored prompt stale (`GrammarQuizQuestion.statement` has the identical property). `purposeFilter` keeps the writing quiz's rule that an expression with no `purpose` matches every filter. **No `expression_progress` / SRS / "already-correct" bucket** — expressions carry no progress data at all.
  - `routes/translation.ts` / `routes/speaking-writing.ts` — SSE streaming via POST endpoint. **The SSE preamble is shared**: `sse.ts:openSSE(request, reply)` returns `{sendEvent, close}` and owns the headers, socket-timeout disable, 15s keep-alive comments and the destroyed-guarded teardown — used by these two routes and `routes/import.ts` (which used to hand-roll the same ~30 lines each). After `openSSE` the response is hijacked from Fastify: validation that should 4xx must run BEFORE it, failures after it are `sendEvent("error", …)`, and `close()` belongs in the `finally`.
  - `routes/translation.ts` — `language` prop = **target** language (active study language); user selects source. Two-step: decompose (MINI, source-lang prompt) → translate (FULL, target-lang prompt). Output uses `passages[].{ sentenceIds[], translation }` — LLM may group consecutive sentences. `buildTranslateSystemPrompt` appends source/target + approach guidance + optional user `context` (situation/register hint, persisted on `TranslationEntry.context`) to the Firestore prompt without needing a migration — context must stay LAST so the static prefix keeps hitting OpenAI prompt caching. The decompose schema omits sentence/chunk/component IDs; `ensureDecompositionIds` assigns them positionally server-side (tolerates old ID-carrying outputs). `/translate-stream` accepts an optional `decomposition` body field — the client (`TranslationView`) replays the previous `decompose-result` on regenerate for unchanged text+source so step 1 is skipped. `TranslationView`'s loading phase live-renders passages from the partial stream via `extractStreamingPassages` (passages are the first key in the translate response).
- **Database**: `firestore.ts` — `updateWord` per-sentence-merges old example `segments` onto incoming `examples` when sentence text is unchanged, so `WordFormModal` (which doesn't carry segments through form state) doesn't wipe LLM-generated pinyin on save. `getCanonicalSegmentPinyin(word)` returns `undefined` for polyphonic words so callers keep the LLM-generated contextual value. `getNextWordId` and `getNextExampleId` use Firestore transactions (not get-then-increment) to prevent duplicate IDs under the `CONCURRENCY=4` parallel smart-add queue — duplicate IDs cause one word to clobber another's doc and leave a ghost `word_index` entry. `checkTerms` validates `word_index` entries via `wordEntryIsLive` to filter out orphaned/mislinked entries before reporting a word as "existing". **`lookupWordsByTerms` (the BULK lookup) drops terms holding neither a letter nor a digit** (`isLookupableTerm`) before reading: callers hand it whatever the segmenter produced — LLM segment texts, import rows, chip splits — and `/`, `：`, `。`, `……` can never be words, so one guard at the choke point covers smart-add segment linking, the word PUT, check-terms, grammar, and the import analysis alike (a skipped term yields no match, which is the shape every caller already handles). Digits count, because `wordIndexDocId` makes terms like `24/7` storable and a letters-only rule would leave such a word permanently unfindable. The single-term `lookupWordByTerm` is deliberately NOT filtered — a false "not found" there backs the smart-add duplicate check and would wave a duplicate word through.
- **LLM**: `llm.ts` — **`callLLM(opts)` is the SINGLE entry point for every model call in the app** (it replaced seven hand-expanded `callLLM*`/`callLLMFull*`/`streamLLM*` variants that differed only in these axes — do not reintroduce per-combination functions; a new knob is a new optional field on `LLMCallOptions`). Options: `system`/`user` (the two messages), `route` (REQUIRED — see below), `tier?` (`"mini"` default | `"full"`; only the FALLBACK when `config/llm_models` has no assignment), `schema?` (present → `response_format: json_schema`, absent → `json_object`), `onChunk?` (present → streaming with a 30s idle abort; the accumulated full text is returned either way). The API key and the two tier defaults come from `.env` (local) or Firestore `config/llm` (deployed), resolved once and memoized forever by `ensureInit`. Every call records per-feature token usage via its `route` label, and `llm-features.ts` reuses those exact labels as model-configuration keys. `LLM_FEATURES` groups the route labels into 12 user-facing features (a stream and non-stream variant of one job share a row); a route that isn't listed — the `scripts/*` ones — falls through to the tier default.
  - **Adding a new LLM feature is a two-step recipe**: ① call `callLLM({..., route: "<area>/<action>"})` at the new call site; ② register that route in `llm-features.ts:LLM_FEATURES` (new entry, or append to an existing feature's `routes`) so it becomes assignable from the LLM Models screen and readable in Metrics. That is ALL — never hardcode a model name anywhere in the repo (the catalog lives in Firestore `config/llm_models`, written by the in-app LLM Models screen; updating which models exist requires NO code change).
  - **Resolution order**: `config/llm_models.features[featureKey]` → `config/llm_models.defaults[tier]` → the env / `config/llm` value. This **inverts** `loadLLMConfig`'s "env always wins" rule, and only for model *names*: per-feature assignment has no env equivalent, and a settings screen whose saved value silently does nothing is broken. It can only ever affect a local dev — `deploy.sh` sets exactly one env var on Cloud Run (`FIRESTORE_DATABASE_ID`), so in production there is no competing env value at all. The order is implemented in exactly TWO functions, both in `llm.ts` side by side so they cannot drift: `resolveModel(tier, route)` (one call) and `resolveEffectiveModels(config, fallbacks)` (all features at once, consumed by `routes/llm-config.ts` for the settings screen's `effective` display — that route no longer carries its own mirror of the rule).
  - **`config/llm_models` is read through a 30s TTL cache, NOT memoized like `initPromise`.** The settings screen writes it at runtime and Cloud Run runs several instances, so invalidating only the instance that served the PUT would leave the others on the old model until the next deploy. `invalidateModelConfigCache()` (called by `PUT /api/llm-config`) makes the writing instance instantly consistent; everyone else catches up within 30s. `readModelConfig` **never throws** — seven code paths now depend on a Firestore read that previously wasn't in the picture, so a blip degrades to the last known value, then to env. A single in-flight promise is shared so the `CONCURRENCY=4` smart-add queue doesn't fire four reads the moment the TTL lapses.
  - `ensureInit` now nulls `initPromise` on rejection. It used to cache the failure for the process lifetime, so a first call made before the config was reachable kept rethrowing the same stale error even after the config was fixed.
- **`routes/llm-config.ts`** (`/api/llm-config`) — `GET /` (assignments + `effective` model and `source` per feature + the env `tierFallbacks`; **structurally cannot leak `OPENAI_API_KEY`**, which lives in a different document), `PUT /` (rejects unknown feature keys rather than storing config the UI could never display or clear), `POST /test` (two probes — `models.retrieve` answers "does this name exist" on its own, since a failed completion alone can't distinguish a bad name from rejected parameters; the provider's error text is returned verbatim, and a successful test calls `ensureModelInCostConfig` so the model shows up on the Costs tab immediately), `GET /available` (`models.list()`, unfiltered and newest-first — filtering by name prefix would reintroduce hardcoded model knowledge, which this repo has none of). `/test` deliberately bypasses `recordUsage`: a settings probe is not study activity.
- **Types**: `types.ts` — `Word` carries optional `hanjaReadings?: HanjaReading[]` (`{ simplifiedChar, traditionalChar, hunEum[] }` per character)
- **Type mirroring**: `backend/src/types.ts` and `frontend/src/types.ts` share translation interfaces (`TranslationResult`, `TranslationPassage`, `TranslationEntry`), grammar/example shapes (`Grammar`, `GrammarExample`, `ExampleSentence`, `GrammarSettings`), expression shapes (`Expression`, `ExpressionGroup`, `ExpressionQuizSubsession`, `ExpressionQuizDirection`, `ExpressionRecallQuestion`, `ExpressionRecallSession`), AND combined-quiz shapes (`CombinedQuizQuestion`, `CombinedQuizSession`, `CombinedDomainWeights`) and import shapes (`ImportExtractedWord`, `ImportExtractedGrammar` — note its `excerpt`) — update both files together. The same convention covers small pure helpers: `termOccurrences` and the inflected/verbatim language split exist in BOTH `backend/src/import-analysis.ts` and `frontend/src/utils/importSession.ts`, deliberately copied rather than shared, and must be kept in step — the server repairs a fresh analysis with those rules and the client repairs a saved session with them, so a divergence means the two disagree about which rows are misfiled.
- **`userSplits` contract**: Chinese examples in both `WordFormModal` and `GrammarFormModal` strip `[\s　]+` from the sentence on save and attach `userSplits: string[]` (the segment texts). Backend routes (`vocab.ts`, `grammar.ts:resolveExamplesToIds`) feed `userSplits` to `fillSegmentPinyin` + `lookupWordsByTerms` to produce `example_sentences.segments` with word IDs. `GrammarExample.userSplits` is input-only — never persisted. It is declared in the smart-add body schema; it used to survive only because that examples item schema has no `additionalProperties: false`, so tightening the schema would have silently killed the chip flow. **In the word PUT, all three segment→word lookups go through `vocab.ts:linkSegmentTerms`, which degrades to "no links" on failure rather than throwing.** Linking is enrichment, and those calls sit INSIDE the example loop — example docs, indexes and `appearsInIds` are already committed by then while the word doc is not — so a throw would strand example sentences the word never gets to reference. Same reasoning and same shape as the `segmentBatch`/`fillSegmentPinyin` catches beside them, and a missing link is exactly what `POST /:language/sync-segment-links` and `scripts/backfill-segment-word-ids.ts` repair. Lookups that fail cleanly BEFORE any write (smart-add, `grammar.ts:resolveExamplesToIds`, `updateSegmentWordLinks`) stay unguarded on purpose.

### Data Storage
- **Firestore** (database ID: `vocab-database`). Key composite keys: `progress`/`flagged_words` use `{language}_{wordId}`; `example_sentence_index` uses `{language}_{sha256(sentence).slice(0,16)}`; **`word_index` is keyed by the TERM, not the id** — `{language}_{term}`, with the numeric word id stored as the `id` FIELD. Because a term is arbitrary user/LLM text, that component goes through **`wordIndexDocId()` (`backend/src/word-index-id.ts`, pure)** at every one of the seven call sites in `firestore.ts` (`addWord`, the `updateWord` collision check + rename delete/set, `deleteWord`, `lookupWordByTerm`, `lookupWordsByTerms`) and in the six scripts that build the same key. It is the **identity** for ordinary terms, percent-encodes `%` and `/` (`%` FIRST — escaping the escape character last would corrupt it), and falls back to `{language}_%23{sha256(term).slice(0,32)}` past 1500 bytes or for the reserved `__…__` shape; the three output classes are disjoint, so it is injective. Identity-for-legal-terms is what makes it a **zero-migration** change: a `/`-bearing term could never be stored (every write path threw at `.doc()` first), so only `%`-bearing terms move — audited and repaired by the MISKEYED pass of `sweep-orphaned-word-index.ts`. Without the encoder, `/` (Firestore's path separator) turns the ID into a multi-component path: an odd count 500s the request, and an **even** count silently reads/writes a doc in a nested subcollection invisible to every `where("language","==",…)` sweep. That is not theoretical — the smart-add LLM segmented an article's ticker annotation as one segment (`09988.HK/NYSE : BABA`) and the segment→word lookup crashed on it.
- `example_sentences` — normalized; words store `exampleIds` and `appearsInIds` arrays referencing this collection. **Grammar items also reference this collection** via `grammar_items.exampleIds[]`; the reverse link is `ExampleSentence.appearsInGrammarIds[]`. A sentence shared by a word and a grammar item resolves to ONE doc via the sha256 dedup index. Orphan deletion (in `deleteWord`, `deleteGrammarItem`, and the vocab/grammar PUT routes) MUST use `isExampleReferencedByAny` so vocab deletes don't clobber grammar-owned examples (and vice versa). `validate-invariant-all.ts` enforces the bidirectional invariant `ES.appearsInGrammarIds == { gId | grammar(gId).exampleIds ∋ ES.id }`.
- `config` subcollections: `config/llm`, `config/llm_models`, `config/auth`, `config/token_costs`, `config/speaking_writing`, `config/translation`, `config/vocabulary`, `config/grammar`, `config/grammar_settings`, `config/import`
  - `config/llm_models` fields: `catalog` (registered model names), `defaults` (`{mini?, full?}`), `features` (featureKey → model name), `updatedAt`. **UI-owned, and deliberately NOT part of `config/llm`** for two reasons: `migrate-llm-config-to-firestore.ts:52` does a full `.set()` on `config/llm`, so anything stored beside the API key would be wiped by the next `./deploy.sh --llm`; and keeping the key in a separate document means `GET /api/llm-config` structurally cannot leak it. Created by the first save from the UI — there is no migration script and `deploy.sh` is untouched.
  - `config/auth` fields: `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `OAUTH_REDIRECT_URI`, `SESSION_SECRET`, `ALLOWED_EMAILS` — see the Authentication section. **The doc's absence is meaningful**: it is the signal that auth is off.
  - `config/import` fields: `analyzeSchema`, `analyzePrompts` (keyed by backend language NAME) — local source in `backend/DB/import/`; push with `migrate-db-config-to-firestore.ts --prompts`. `routes/import.ts` loads it LAZILY so a missing doc can't stop the server from booting — and **memoizes it for the process lifetime**, so a prompt/schema change needs a push AND a restart (locally: restart `npm run dev:local`; deployed: `./deploy.sh … --prompts`, which is why the push and the revision roll are one flag).
  - `config/translation` fields: `decomposeSchema`, `decomposePrompts`, `translateSchema`, `translatePrompts` — local source in `backend/DB/translation/`; push with `migrate-db-config-to-firestore.ts --prompts`
- `import_sessions` — one paused, resumable article review each (auto-ID docs with a `language` field, listed by an in-memory `updatedAt` sort to avoid a composite index — the `translation_history` pattern, NOT the singleton-per-language quiz/speaking pattern, since several articles can be in progress at once). Holds `paragraphs` + the flattened `items` working copy + destination groups; see the `ImportView.tsx` entry below for the item model.
- `expression_items`, `expression_groups` — per-language, mirror the grammar collection structure. Note expressions are keyed by **ISO code** (`"en"`), whereas words and grammar use the full-name URL segment (`"english"`) — the expression components are passed `isoCode`, and passing `language` instead yields an empty pool with no error. `ExpressionQuizSubsession` (the writing quiz) is NOT a separate collection; it is stored as `SpeakingWritingSession.expressionQuiz?` in `speaking_writing_sessions`.
- `expression_recall_sessions` — the **recall** quiz's own collection (doc id = language code). Separate from `speaking_writing_sessions` on purpose: see the co-tenancy note under `routes/expression-quiz.ts`.
- **Meta-groups (`category`)**: `word_groups`/`grammar_groups` docs carry an optional `category?: "A" | "B"`. **Absent = "A"** and only `"B"` is ever written, so every pre-existing group is Group A with zero migration. "A" is the universe of all items (every existing flow — drafts, chips, browse filters, word/grammar/combined quiz setup — filters to A via `types.ts:categoryGroups`); "B" is the not-yet-memorized subset drilled by the Group B quiz. `defaultWordGroup`/`latestGrammarGroup` both consider category A only, so a B group is never an implicit default. **They are deliberately asymmetric**: words take the highest-PRIORITY A group (`categoryGroups(groups,"A")[0]`, order-dependent — never re-sort the array locally, which is what made `ExampleSentenceEditor`'s old `createdAt` sort a silent bug), while grammar still takes the most recently CREATED one, because `GrammarGroup` has no `order`, grammar groups are not reorderable, and grammar is exempt from one-item-one-A-group — so there is no grammar priority to read. Group B membership is added on top of A by the shared `GroupBSelect.tsx` chips (every add flow assigns an A group, which is what upholds "a B item is always also in A" on the ADD side — that half is client convention only; the importer's Group B button keeps it by writing the A destination too whenever it has to create the item). **The REMOVE side of that invariant IS enforced server-side**: `firestore.ts:removeOrphanedWordsFromCategoryBGroups` / `removeOrphanedGrammarFromCategoryBGroups` strip an item from every B group once it belongs to NO category-A group — called best-effort (outside the transaction, mirroring `removeWordsFromOtherCategoryAGroups`) from the `remove` branch of both `modify*GroupMembers` and from `deleteWordGroup`/`deleteGrammarGroup`, since deleting an A group orphans its members the same way. The remaining-A-membership re-check (rather than an unconditional strip) is what keeps a MOVE between A groups inside its B sets, tolerates legacy duplicate A memberships, and makes the same rule correct for grammar's legal multi-A membership. ⚠ Its race direction is worse than the add side's: losing to a concurrent A-add wrongly strips B and nothing re-adds it, which is why the four client "move" call sites (`WordList.handleUpdateWord`, the `useWordQueue`/`useGrammarQueue` update items, `GrammarFormModal`'s edit diff) sequence their adds strictly BEFORE their removes instead of one `Promise.all`. B memberships stranded before this enforcement existed are not retro-cleaned; `POST /groups/normalize` re-files such words into the top A group (the gentler repair). **A Group B group spans both domains**: unlike Group A, where a word group and a grammar group are unrelated sets, one Group B study set holds words AND grammar. It is still stored as two docs (one `word_groups`, one `grammar_groups`, both `category: "B"`) joined by NAME — `frontend/src/utils/groupB.ts` (`UnifiedGroupB`, `loadGroupBGroups`, `createGroupBGroup`, `resolveGroupBTargets`) is the merge/create/resolve layer, and `GroupBUnifiedSelect.tsx` is the name-keyed picker built on it (with inline "new group" creation, which creates both sides at once). `resolveGroupBTargets` only materializes the side a registration actually needs, so importing an article with no grammar never leaves an empty grammar group behind. The per-domain `GroupBSelect.tsx` stays in use by the single-domain add forms. Category is fixed at creation (no PUT). `firestore.ts:removeWordFromCategoryBGroups` / `removeGrammarFromCategoryBGroups` back `DELETE /:language/group-b/members/:id` on both vocab and grammar. **Reorder invariant**: `PUT /vocab/:language/groups/order` still requires EVERY group of the language exactly once, so `GroupPickerModal` appends the hidden category's IDs after the visible reordered ones.
- `word_groups` — per-language groups own membership through `wordIds[]` and may carry numeric `order`. **`order` is a PRIORITY, not just a display order** (`firestore.ts:compareWordGroups`, the single definition, shared by `getWordGroups` and the normalize routine): index 0 is the highest, and the top category-A group is simultaneously the default target of every "add a word" flow (`frontend/src/types.ts:defaultWordGroup`) and the group `POST /groups/normalize` files ungrouped words into. An explicit `order` wins; without one the fallback is **newest-created first**, so the group you just made is the one being filled. A group with no `order` still sorts after every group that has one — a stated priority beats an implied one. The first reorder backfills a complete zero-based order for all groups; **new groups are inserted at `min-1`, i.e. the TOP** (not appended — `max+1` would hand the default add target to the oldest group). Negative values are transient: the next drag renumbers 0..n-1. Legacy data whose `order` is literally the creation sequence is repaired once by `scripts/reprioritize-word-groups-newest-first.ts`.
- **Category A is EXCLUSIVE for words**: a word belongs to at most ONE category-A word group, so adding it to one is a **MOVE** — `firestore.ts:modifyWordGroupMembers` calls `removeWordsFromOtherCategoryAGroups` after the add. The A groups are the lesson structure, a partition of the library rather than overlapping tags, so a word that reappears in a later lesson belongs to that lesson only. **Grammar is NOT subject to this** (a grammar item may still sit in several A groups), and category B never is — a B group is the not-yet-memorized subset drawn on top of A and several may hold the same word. The removal runs OUTSIDE the caller's transaction (mirroring `removeWordFromCategoryBGroups`): Firestore wants all of a transaction's reads before its first write, while "which other A groups hold this word" is only knowable after the target doc has been read; losing the race leaves a word in two groups, which the next add repairs and `scripts/dedupe-word-group-membership.ts` sweeps. **`POST /api/vocab/:language/groups/normalize` is the third enforcement point and the only user-facing one**: it re-files a whole language by group PRIORITY — a word in several A groups keeps only its highest-priority membership, a word in none (including one that sits only in a Group B set — legacy data from before the remove-side B-strip closed that hole) joins the top group, and B is untouched. Note it and the dedupe script pick DIFFERENT survivors: the script keeps the most recently created group, the endpoint keeps the highest-priority one. The script stays useful as an independent duplicate *detector*; prefer the endpoint for repair. Every add path in the app funnels through this one function, which is why no caller has to cooperate — but the pickers were made honest anyway: the Group A chips in `WordFormModal`/`SmartAddWordModal` are **single-select**, and `GroupPickerModal.handleAddToGroup` re-reads the collection after an add (patching one group locally would leave the source group's count stale).
- **Local files**: `backend/DB/` (grammer, speaking&writing, translation, vocabulary, backup, old, original). Word JSON is no longer mirrored locally — Firestore is the source of truth; `old/` and `original/` hold pre-migration HSK archives.
- **Docs**: `docs/draft-json-format.md` (draft upload format) · `docs/word-grammar-crud.md` (Word/Grammar storage model, Group A/B semantics, the full CRUD route table, and the 2026-07-29 live verification report) · `docs/group-ab-crud-audit.md` (the 2026-08-01 Group A/B CRUD + interruption-consistency audit and fixes: deletes now cascade into group membership/flags/progress in one batch — closing word-grammar-crud's F1 — word/example doc+index writes are batched, category-B group creation is idempotent by name, and the queues no longer rescue an already-created word as a draft).

    - **Item model** (`utils/importSession.ts`, all pure): the analysis's positional `words[]`/`grammar[]` are flattened once into `ImportItem[]` with stable client ids — the raw arrays are NOT persisted, so there is one working copy and no drift. **A word row's `order` is the term's CHARACTER OFFSET in its sentence**, not its index in the analysis array: array order is only as good as the model's willingness to emit words in sentence order, and offsets are what let a materialized gap row slot into reading order. The nth listing of a term takes its nth occurrence (counted per term — a shared cursor would mis-place every word emitted out of order, which is the case this repairs); a term that is not a substring at all (routine for Japanese/Korean, where the prompts split inflections) gets `previousOrder + 0.001`, a step small enough never to collide with a gap run's integer offset. `order` is still **fractional** so a split inserts its parts between neighbours without renumbering — safe against offsets because `splitWordItem` keeps all parts strictly inside `(o, o+1)` while a term of length L pushes its neighbour to `o+L`. Order is computed at BUILD time only; `undoDerivation` restores the original values. Merge/split/delete **tombstone** their sources (`status:"skipped"` + `supersededByIds`) rather than removing them, which is what makes `undoDerivation` possible and keeps the session a complete record. `mergeWordItems` derives the new term from the sentence SPAN the sources cover (`sentenceSpanForTerms`), not naive concatenation, falling back to concatenation when a term isn't a literal substring; it always drops `meaning` (a compound's gloss is not the sum of its parts). **Readings are merged and split automatically**: `mergeTransliteration` joins the sources' readings whenever the merged term is exactly those sources concatenated (right by construction — no syllable arithmetic can improve on it), and `splitTransliteration` binds one syllable per character. Both go through `readingSyllables`, which prefers whitespace boundaries and falls back to `tokenizePinyin` — a longest-match-with-backtracking cut over a table of every toneless Mandarin syllable, plus the rule that a candidate carrying two tone marks is two syllables (which is what tells 「xīān」 from 「xiān」). Non-pinyin readings (kana, hangul) fail to tokenize and come back `undefined` rather than mis-cut. A reading is dropped only when a source had none, or when the merge spans MORE than its parts (「食べ」+「みる」 over 「食べてみる」) so the joined reading would sit off its characters. Merge has two affordances: the per-row "↓と結合" button (merge with the row below — the common case) and the multi-select checkboxes.

    - **Coverage** (`utils/importSession.ts`: `sentenceCoverage` / `coverageRuns`, pure): the counterpart to exhaustive extraction — which characters of a sentence the live word rows account for. A character is in scope when it matches `\p{L}`; punctuation, spaces, digits and symbols never are, so 「。」 can't hold a sentence back. A term covers EVERY occurrence of itself in the sentence (the prompt lists a repeated word once), found through `termOccurrences`: **a Latin-script term matches only at word boundaries and case-insensitively**, without which the English article 「a」 marks the `a` inside 「analysis」 and coverage is so over-claimed that no English sentence ever reports a gap. CJK terms keep plain case-sensitive substring matching. **`sentenceCoverage`/`materializeGaps`/`buildImportItems` all take the `language`**, because what a non-matching term means depends on it. If a term isn't a substring at all, the longest prefix that is covers its FIRST occurrence only and sets **`SentenceCoverage.approximate`** (that search starts at index 0 rather than where the word belongs, so the covered flags — and the gap runs derived from them — may sit on the wrong characters) — but **only in Japanese and Korean, and only for a prefix of ≥2 characters** (`MIN_PREFIX`). In Chinese and English a term that isn't there accounts for NOTHING and is reported as a misattribution instead. That gate is a bug fix, not a tidy-up: a misfiled Chinese word whose single-character prefix happened to occur (「一」 in 「一年间」) used to mark some unrelated word as covered AND flag the whole sentence approximate, which makes `materializeGaps` refuse to run and hides the manual button behind a passive hint — so one misfiled word silently voided the "every character has a row" guarantee for the entire sentence. **Grammar rows never contribute**: a `statement` is pattern notation (「随着～，越来越～」), not a substring, so it cannot be matched positionally (which is what `excerpt` is for, server-side).
    - **Mismatch detection is DERIVED, never persisted** (`wordMismatch` / `mismatchedWords` / `findWordHome` / `reattachMismatchedWords`, all pure and all mirroring `backend/src/import-analysis.ts` rule-for-rule). `ImportItemBase` gained no flag: a persisted one goes stale the instant the user edits a term, and re-running `termOccurrences` per row per render is free. This is the repair path for sessions saved BEFORE nesting — no amount of schema or prompt work reaches data already on disk. `ImportSentenceCard` renders a mismatched row as a **fourth visual state** (rose border + badge, ranked ABOVE the green "already in the library" tone, since a row on the wrong sentence is wrong either way) with a "move to sentence N" button, and **refuses both A/B registrations where `requiresVerbatimTerms(language)`** — registering writes `sentenceText(sentenceIndex)` as the word's example, so the wrong sentence would be persisted into the words collection permanently. `ImportReview` shows a session-level banner with a bulk fix. It is an **explicit press, not a repair on load**: autosave would persist a silent bulk rewrite with no undo. `reattachMismatchedWords` tombstones (`status: "skipped"`) rather than moving when the destination already lists the term, leaves an unmatchable row in place still flagged, skips rows already registered (their example is written; moving now would make the session claim it was registered from a sentence it never saw), and re-runs `materializeGaps` **only for the sentences rows moved OUT of** — a sentence that gained a row cannot have gained a gap, and a blanket re-run would resurrect gap rows the user deliberately deleted.
      **Gaps become real rows, not just a highlight** (`materializeGaps`): `buildImportItems` runs it over every sentence, so "every word of every sentence is on screen" holds from the moment the review opens rather than depending on the user noticing an amber run. One run = one row (`origin: "gap"`, amber left border, no reading/meaning, a "type a space to split it" hint) — guessing internal boundaries would invent a segmentation nobody asked for, and `splitWordItem` is one keystroke away. It **refuses to act on an `approximate` sentence**, where the runs are a guess; those keep the highlight plus a manual "add the uncovered text as rows" button, which is also how a gap reopened by a later edit is closed. `origin: "gap"` is load-bearing beyond styling: `useImportLibraryStatus` skips `origin === "llm"` rows for `check-terms`, so a gap row — never part of the server's `existing` map — must not claim to be one. `ImportReview` memoizes a `sentenceIndex → missing` map so each collapsed row leads with its gap count; a rescan per render would be O(sentences × items).

The sticky is bounded by the CARD's box, so it releases by itself once the card scrolls past and collapsed sentences are untouched; negative margins cancel the card's `p-3 sm:p-4` so the bar spans full width, the background must be opaque (`bg-gray-800/95 backdrop-blur` — the card is `bg-gray-800/60` and rows would show through, the same treatment as the mobile prev/next bar), and `z-20` sits below `PinyinInput`'s `z-30` palette so readings still open over it. **Only the sentence is pinned**: the translation and the coverage line stay OUTSIDE and scroll away — the translation is a reading aid consulted once and the coverage line an occasional action, and on a phone every pinned line is working area that the rows below never get back. `max-h-[40vh]` caps a very long sentence.

      **The review screen must NOT be a scroll container, and every sticky here depends on that.** `Dashboard`'s shell is `min-h-screen` with a `flex-1` main, and a flex item's default `min-height: auto` lets it grow to its content — so **the document is what scrolls** (`QuizTaking` carries the same note, and its stickies work). `ImportReview`'s root used to be `h-full overflow-y-auto overflow-x-hidden`, where `h-full` resolved under that shell to "exactly as tall as its content": an overflow container that never scrolled. Since `position: sticky` anchors to its nearest SCROLLPORT ancestor, that silently made **every sticky in the importer inert** — the pinned sentence, the mobile prev/next bar and the `lg:sticky` destination rail all just scrolled away with the page (the prev/next bar sits at the end of the content, so nobody noticed it had never pinned). It is now `min-h-full overflow-x-clip`: `overflow-x: hidden` promotes the other axis's `visible` to `auto` per the CSS overflow spec and so creates a scrollport all by itself, whereas `clip` is the one value that coexists with `visible` — it stops sideways overflow without establishing a scroll container. The other `ImportView` phases keep the old wrapper; they hold no sticky.

      **Pressing the focused sentence again folds its rows away** (the ▲ in the pinned bar does the same). The open/shut flag is LOCAL state in `ImportReview`, deliberately not `focusedSentenceIndex`: that field is session data and required on the wire, so "which sentence" and "open or shut" stay separate rather than smuggling a `-1` into the saved document — prev/next still steps from the folded sentence, which keeps a ring to show it is current. `focusRef` is a callback ref carried by whichever shape the focused sentence has (open card wrapper or collapsed row) and `collapsed` is a dependency of the scroll effect, because folding removes hundreds of pixels from ABOVE the scroll position. Tapping the sentence text is the same gesture as selecting a term from it, so the handler refuses to fold while a selection is live and spends a bare tap on dismissing a pending "add as a word" offer first.
    - **Registration is per item AND per destination.** `registerItem(id, target)` writes ONE destination: `"A"` the Group A lesson group, `"B"` the Group B study set — two buttons on every row (`RegisterControls`/`DestinationButton` in `ImportSentenceCard.tsx`), coloured like the destination rail's dots (**A indigo, B amber**) and labelled with the chosen group's NAME plus an A/B badge. One button could not express "already in A, still needs B", the ordinary state of an article that repeats vocabulary the user already owns. A **B press also writes the A destination when the entity does not exist yet** — a Group B group is the not-yet-memorized SUBSET of A, so an item created into B alone would be missing from the browse lists and every Group A quiz — but an item already in the library is left where it is, so pressing B never moves a word out of its lesson. `groupBIdsFor` is therefore resolved only for a B press: it CREATES the missing half of a B set, and an A press has no business materializing one. **The ✓ is read from actual membership** (`GroupMembership.aIds` — group IDs, since the A destination is chosen by ID — plus `b` by NAME, which is how a B set is joined across domains), never from `status`: status is the outcome of the last write this review made, while the question on screen is where the item sits now. `status` only drives the transient states. **Those transient states are PER DESTINATION** — `ImportItemBase.registrations: Partial<Record<"A"|"B", ImportRegistrationState>>` is the real record, and `status`/`target`/`error` are a derived summary of it (`utils/importSession.ts:summarizeRegistrations`, always written through `withRegistration` so the two cannot drift). A single status could only describe one write, so pressing Group A left the Group B button dead until A settled, and "A failed but B succeeded" had no representation at all. Summary precedence is **queued > failed > duplicate > registered**: a row with anything in flight stays `queued` (hence `isLocked`, so its text can't be edited mid-write), and once everything settles a failure outweighs a success because that is the row the user still has to deal with. Everything downstream — `isLocked`, `sessionCounts`, the load-time reconciliation, the backend's `registeredCount` — still reads the summary and needed no change. Consequences: the entry guard refuses only `skipped` rows and a destination **already queued for itself**, and `DestinationButton`'s `disabled`/`busy`/`failed`/`error` all come from that destination's own slot (`disabled={stateA?.status === "queued"}`, not the row's). The piggyback guard likewise matches per destination. **Creates are serialized per term** by `createChain` (a `useRef` map of `kind term` → the in-flight create): two presses on a row whose entity does not exist yet would each call smart-add for the same term, and the server's duplicate check can pass both and store the word twice — so the second press awaits the first, re-reads the row, and finds the learned id, which turns it into the cheap group-add path. Group adds are set-based and idempotent, so they are never chained. The claim is released from `settle`, and the enqueue calls are wrapped in `try/catch → fail` because a throw there would leave the chain claimed and every later press for that term waiting forever. A row loaded still `queued` has its pending destinations settled by `load`'s `check-terms` reconciliation, or its button would spin (and stay disabled) for good.
    - **Registration records the real outcome.** `useImportSession.registerItem` enqueues ONE item and records it. Status is never inferred from `succeededTerms` — that set is term-keyed (so two rows sharing a term are indistinguishable), success-only, and in-memory. Instead both queue hooks gained an optional `onSettled` in their create options (`WordCreateOptions`/`GrammarCreateOptions`), invoked from the existing `.then`/`.catch`; the catch settles only after the draft-rescue resolves so `rescuedAsDraft` is accurate. **`onSettled`'s success payload carries the created entity's ID** (`wordId`/`grammarId`) — `processItem` already held it and used to throw it away, forcing the ID to be rediscovered through a debounced `check-terms`. On load, EVERY library claim is reconciled, not just `queued` rows (`utils/importSession.ts:reconcileLibraryClaims`, pure and vitest-covered): word rows claiming presence (`existingWordId`, or status queued/registered/duplicate — tombstone ids included, since `registeredTerms` counts them) are re-verified by term via `checkTerms`, grammar rows by id via `POST /items/batch` (missing ids are omitted from its response). A claim the DB disproves — the word was deleted from the browse tab since the last visit — is reset to `pending` through the registrations record (success and dead-tab `queued` slots pruned, `failed` slots kept; tombstones only lose the id) so the row stops rendering "already in your library" and becomes registrable again; a confirmed claim keeps/refreshes its id (delete-then-recreate included) and a still-`queued` row settles as before. The two probes are independent and best-effort (`Promise.allSettled` — a failed probe leaves that domain untouched), and a changed reconciliation is flushed immediately, so the session doc — and the `registeredCount`/article-quiz pool derived from it — self-heals on open rather than on the next edit. Grammar rows with no id stay visibly unverified (no term-level check exists).
    - **Sibling propagation, and what is NOT propagated** (`useImportSession.applySettle`): an article repeats its vocabulary, so the entity ID a registration learns is knowledge about the TERM, not about that row. One `setItems` writes the outcome to the row and `existingWordId`/`existingGrammarId` to every live row sharing the trimmed term (word) or statement (grammar) — two `immediate` patches would each flush and cost a second PUT. Those siblings then render "already in your library" and their button takes the group-membership-only path. **Status is deliberately NOT propagated**: marking untouched rows `registered` would inflate the progress counter and `isLocked` them out of "Add to groups" after the destination changes. The lone exception is a row left `queued` by the **piggyback guard** — `registerItem` refuses to enqueue a second write for a term already in flight (the queue runs 4 at a time, so it would race, and at best return 409 with its group work skipped), and such a row has no write of its own to wait on, so it must inherit the leader's terminal status (including failure) or it spins forever.
    - **409 recovery.** A word 409 means the word IS in the DB but `smart-add` threw before the queue's group work, so nothing was written — and group membership was the whole point of the row. `registerItem` recovers the ID via `checkTerms`, applies `modifyGroupMembers` (set-based, so re-adding is a no-op) and settles as `registered`; only if recovery fails does it fall back to the neutral `duplicate`. Grammar needs no such branch — a grammar 409 is unreachable.
    - **Group membership is one read, shared** (`hooks/useImportGroups.ts`): the review screen used to fetch `getGroups` three times — the destination rail, the membership hook, and `GroupBUnifiedSelect` via `loadGroupBGroups` — for identical documents, and `WordGroup` already carries `wordIds`, so the membership data was on screen twice and discarded once. `useImportGroups` holds both collections with a debounced `reload()` (`getWordGroups` is O(library size) and registrations arrive in bursts), passed to `ImportDestinationRail` as props and to `useImportLibraryStatus`. The rail seeds `autoSelectLatest` **once per language** via a ref, so a post-registration reload cannot silently move the user's chosen destination.
    - **`useImportLibraryStatus` inverts BOTH categories** into `entityId → {a: string[], b: string[]}` of group names, for words and grammar alike. Real group names distinguish "in the library" from "in the group this review is filling" — but `inLibrary` stays the fallback signal, because a term can be in the library and in no Group A group at all, and a word proven to exist by a 409 whose recovery failed has no ID to look names up by. `useImportSession.membershipOverlay` (`entityId → groupIds`, transient, cleared on session change) is **unioned** over the read to cover the gap between a write returning and the reload landing — it is not persisted on the items, since the server is the record and the reload answers the same question.
    - **Autosave**: debounced ~1.2s for free-text, flushed immediately for every status/destination change, on unmount and on `close()`. One PUT in flight at a time (`savingRef`/`pendingRef`), and only `updatedAt` is taken from the response — local state stays authoritative so edits made mid-request are not reverted. `resolveGroupBTargets` CREATES missing groups, so its result is memoized per domain per `groupBNames` rather than called per add.

  - **Offline-tolerant quizzes** — all four quiz screens (word, grammar, Group A, Group B) pre-build their whole question set and defer their writes, so a bad connection mid-session cannot interrupt a quiz. The expression **recall** quiz shares the WRITING half in full (`answerOutbox` + `quizLocal`) but deliberately skips `useQuizPrefetch`: that hook is hardwired to the word+grammar pair and chunks its requests because a word payload carries definitions, examples and hanja readings, whereas an `Expression` is four short strings — so `ExpressionRecallTaking` hydrates with one `items/batch` call and hand-rolls the `{loading, loaded, total, error, retry}` object `QuizSyncBadge` needs (its prop is structural). It still keeps the hook's two load-bearing properties: the id list is frozen at mount, and a `missing` id counts as *resolved*. Two independent halves:
    - **Reading** — `hooks/useQuizPrefetch.ts` loads every question of the session up front, **keyed by id** (`Map<wordId, QuizQuestion>` + `Map<grammarId, Grammar>`) rather than by session position. That is the whole trick: order changes constantly (retry splices, resume reweighting, weight edits) while the id SET never does, so a reorder is a pure re-render — the old positional paging had to re-fetch after every wrong answer, and `applyWeights` reordered without resetting the fetch high-water mark, silently leaving reordered positions unhydrated. Ids are requested in the order the user will meet them and the list is **computed once and frozen** (a retry re-queue reuses an existing id; nothing ever adds one, so the set is fixed for the session); the **first chunk is small (24)**, the rest streams behind it in chunks of 150 (grammar 100). Only the id set restarts loading, and a retry resumes from what already arrived. Render merges `{...cache.get(id), ...slimQuestion}` — the slim entry MUST win so a stale cache can't overwrite `userCorrect`.
      **Each card is gated on its OWN payload**, not merely on `ready` (which only means the first chunk landed): otherwise card 25 of a 300-card session could reveal with zero definitions while both grade buttons stayed live, recording an answer for a blank card. The hook therefore also exposes **`missing`** — ids the server returned no document for (deleted mid-session) — which counts as *resolved*, or that card would block forever. Failures auto-resume on the `online` event and on a widening 5s→60s timer, not only via the badge's manual retry.
    - **Writing** — `utils/answerOutbox.ts` is a **module-level** (not component-state) serial FIFO queue, so navigating home mid-flush doesn't drop answers; `hooks/useAnswerOutbox.ts` is the React view plus the `beforeunload` guard. `handleGrade` is now synchronous: it applies the server's own session mutation locally through `utils/quizLocal.ts` (pure; mirrors `insertRetryQuestion`, the score bump and the `correctMembership` drop) and advances immediately. It used to `await POST /answer`, and since the `try` had no `catch`, a network failure left the quiz **frozen on the current card**. Order in the queue is load-bearing — the server fills "the first question with this id and no answer yet", so an answer and its retry copy must arrive in sequence. Retries back off 1s→30s and flush on the `online` event; a non-retryable 4xx drops that one answer rather than wedging everything behind it. One entry kind is NOT an answer: **`combinedMembership`**, the mixed quiz's B→A membership refile — a `PUT …/weights` carrying only the membership maps, riding this queue precisely because it is serial (the PUT and a `POST /answer` both read-modify-write the session doc). Its payload is FULL-STATE at enqueue time, so a dropped or superseded entry loses nothing — every later enqueue restates all prior moves. **Exactly one component owns the retry timer**: `scheduleRetry` clears before arming, and `enqueueAnswer` only kicks a drain when no backoff is pending — otherwise every card graded while offline fires its own doomed request and arms another timer, orphaning the previous handle. Client and server question order therefore diverge while offline, which is harmless because every resume path re-draws the tail anyway.
    - **Nothing is persisted client-side.** Per the repo convention (`SettingsModal.tsx:122`), localStorage holds display prefs only. A refresh regenerates the quiz (the resume endpoints reweight the unanswered tail) and, deliberately, discards unsynced answers — hence the `beforeunload` warning.
    - `api/client.ts` exports `ApiError` (carries `status`) and `isRetryableError`. `getCurrentSession`/`getCurrentCombinedSession`/`getCurrentGrammarSession` return `null` **only on 404** and rethrow everything else; they used to swallow every error, so an offline refresh was indistinguishable from "no session" and `Dashboard` bounced the user home. `QuizRecoveryState.tsx` is the retry screen that replaced that redirect, and `EmptyState` uses `Promise.allSettled` so one unreachable domain doesn't hide the other three resume buttons.
    - `nginx.conf.template` enables gzip for `/api/` — these hydration payloads are large repetitive JSON and there is no compression plugin on the Fastify side.
  - `Dashboard.tsx` — URL sub-paths: `/browse`, `/quiz`, `/flagged`, `/grammar`, `/import`, `/grammar-quiz`, `/combined-quiz`, `/group-b-quiz`, `/mixed-quiz`, `/import-quiz-a`, `/import-quiz-b`, `/translation`, `/speaking-writing`, `/expressions`, `/expression-recall`, `/print-worksheet`. Home page sections rendered by `EmptyState.tsx` are driven by `sectionOrder` in `settings/defaults.ts`; add/remove a section key there and add/remove the matching render branch in `EmptyState`. **`CombinedQuizTaking` needs its `key`** in the `/combined-quiz`, `/group-b-quiz` and `/mixed-quiz` branches (`key="combined"`/`"groupB"`/`"mixed"`): all THREE render into the same slot of one ternary, so without it React reuses the instance across variants and a stale `variant` posts answers to the wrong session. Each variant also needs its own state quartet (`active*Quiz`/`show*Setup`/`*ResumePrompt`/`pending*Filters`), its own `subPath` recovery effect, and a reset in `goHome()`. **The two article quizzes break that mould deliberately**: they share ONE state record keyed by category (`activeArticleQuizzes: Partial<Record<"A"|"B", CombinedQuizSession>>`, plus one `articleResumePrompt`/`pendingArticleQuiz`), one recovery effect and one route branch, because the rendered category is derived from the URL (`articleQuizCategory`) rather than stored — so it can never go stale against the route, and `key={`import${category}`}` falls out of the same value. They have no filter modal: the pool is chosen on the import screen and there is nothing to configure. Entry is `BrowseView`'s `onArticleQuiz` pass-through (`ImportView` → `ImportSessionList`'s two header buttons), NOT `EmptyState` — the import screen is the only way in, and Dashboard still owns the start/resume-prompt because `/start` overwrites the session under a fixed key.
  - `LanguageSelectPage.tsx` — the app's only **language-agnostic admin surface**: a System card that swaps the whole page for one of two views via `systemView: null | "metrics" | "models"`. Everything under `/:language` is scoped to one study language, which is why global config belongs here and not in `SettingsModal` (that one is per-user display prefs in `localStorage`).
  - `LLMModelsView.tsx` — the LLM model catalog and per-feature assignment screen, sibling to `MetricsView`. Two tabs: **Model Catalog** (free-text add, per-model Test showing OpenAI's verbatim error, and an on-demand "Load from OpenAI" list) and **Feature Assignments** (tier defaults plus one `<select>` per `LLM_FEATURES` row, each showing its resolved model and a `source` chip). **English-only on purpose**, matching `MetricsView` — these are technical feature names rendered beside raw `route` strings, and translating one admin screen while its sibling stays English would be the inconsistent choice. Only the System-card button label is translated (`viewLLMModels`). A standing banner explains the one coupling to `MetricsView`: a newly used model is auto-registered in `config/token_costs` at **zero** rates (`firestore.ts:ensureModelInCostConfig`), so its spend reads $0 until real rates are entered.
  - `ExpressionRecallQuizView.tsx` / `ExpressionRecallFilterModal.tsx` / `ExpressionRecallTaking.tsx` — the recall quiz. The View owns the resume (it refetches on mount), which is what makes the real sub-path worth having: a refresh on `/:language/expression-recall` lands back in the session. It distinguishes 404 (→ setup) from a transport failure (→ `QuizRecoveryState`) because `api/expression-recall-quiz.ts:getCurrentExpressionRecallSession` returns `null` **only on 404** — unlike the older `getCurrentExpressionSession`, which swallows every error and so cannot tell "no quiz" from "offline". Both entry buttons live inside `EmptyState.tsx`'s existing `isoCode !== "zh"` block (Expressions are already shown for en/ja/ko and hidden only for Chinese — the `showGrammar = isoCode !== "en"` gate that used to hide Group A/B was a different thing, and is gone). The existing writing quiz was relabelled by i18n **value** only (`startExpressionQuiz` → "Expression Writing Quiz"), identifier unchanged, the same trick used for "Group A".
  - `StudyQuizModal.tsx` — three tabs: word (`QuizFilterModal`), grammar (`GrammarFilterModal`), combined (`CombinedQuizFilterModal`, labeled "Group A Quiz"). **All quiz-setup modals scope the pool by GROUP ONLY**: the legacy Levels / Topics / Grammar-Category checkbox columns were removed from `QuizFilterModal` and `CombinedQuizFilterModal` (and `GrammarFilterModal` never had them), so the setup UI shows only word/grammar group selection (plus weights and the "already-correct" bucket). `QuizFilters`/`CombinedQuizFilters` keep their `levels`/`topics`/`categories` fields for backend compatibility but the modals now always emit them as empty arrays (backend `routes/quiz.ts`/`routes/combined-quiz.ts` still accept them; they're simply never populated from the UI). The combined setup modal has word/grammar domain-weight inputs plus per-group weights on BOTH sides; setting a domain weight to 0 excludes that domain. **`CombinedQuizFilterModal` renders two layouts**: single-category scopes (`"A"`/`"B"`) keep the domain-first sections, while the mixed scope is **category-first** — a collapsible Group A and Group B section, each holding its own category weight, then a word block and a grammar block with their own weights and group lists. The nesting on screen matches the nesting being configured, which is the only reading under which a per-group number is guessable. The group lists come from one extracted `GroupChecklist` (used four times in mixed mode, twice otherwise) and are folded below `sm`, seeded once from `matchMedia` so a rotation can't reopen what the user closed. Its `CategoryBadge` was dropped: each list now holds one category by construction. **⚠ Rendering A above B must NOT change `orderedIds`**, which still emits `allWordGroups`/`allGrammarGroups` order — `scopedGroups` returns those B-FIRST, and that is what makes a word in both categories count against B. Validation is per (category, domain): it blocks only when that bucket is weighted, has groups available, and none are ticked — a bucket with no groups at all just shows the inline `noGroupsHint`. **The Group B and mixed A+B quizzes deliberately have NO tab here** — each opens `CombinedQuizFilterModal` standalone from `Dashboard` (`groupCategory="B"` / `"AB"`, both with `showFlaggedToggle={false}`), since they are independent systems on top of the same machinery rather than another way to configure the Group A quiz. The home "Group A Quiz" button (`t("combinedQuiz")`, shown for every language since the English grammar gate was removed) opens the combined tab; `CombinedQuizTaking.tsx` renders per-question by `kind` and prefetches both domains through the shared `useQuizPrefetch`.
