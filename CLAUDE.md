The deploy scripts carry **config uploads only**, and only because config is read
once and memoized for the process lifetime (`routes/import.ts`) or at boot
(`auth-config.ts`) — so pushing it and rolling a revision are one operation. Data
migrations (`migrate-example-sentences.ts`, `migrate-grammar-examples.ts`,
`--archives`) and destructive maintenance (`wipe-grammar-firestore.ts`) used to be
deploy flags and are now run directly; they have no relationship to a release, and
a wipe reachable from the deploy command is one someone eventually runs by reflex.
`migrate-to-firestore.ts` (the old word import) reads `backend/DB/word/`, which is
empty — nothing is uploaded from the local repo any more. An unknown flag is
rejected rather than silently taken as `PROJECT_ID`.

`--llm` still uploads only the three `config/llm` keys (API key + the two tier
defaults). **Per-feature model assignment is not a deploy concern**: it lives in
`config/llm_models`, is written by the in-app LLM Models screen, and takes effect
within 30 seconds without a new revision. That separation is also what stops
`--llm`'s full `.set()` from wiping it.

## Architecture

Full-stack vocabulary quiz app supporting four study languages (`en`/`ja`/`ko`/`zh`; HSK levels apply only to Chinese): **Fastify 5 backend** + **React 19 / Vite 6 frontend**.

### Authentication (Google OAuth)
Single-user access gating, NOT multi-tenancy — there is no `users` collection and no `userId`/`ownerId` on any document, so every signed-in user shares one dataset. Access is an email allowlist.

- **`auth-config.ts`** — resolves config once, **eagerly at boot** (unlike `llm.ts:loadLLMConfig`, which is lazy) because the request hook must know the posture before serving anything. Env vars win, else Firestore `config/auth`. Three outcomes, and the distinction is the whole security posture: env complete → auth on; **`config/auth` missing → auth OFF** with a loud warning (this is what lets the code deploy before the OAuth client exists); **Firestore read threw → `process.exit(1)`**. Never guess "off" from an error — that would reopen the public API on a transient blip. Also owns the stateless session token (`signSession`/`verifySession`) and the PKCE/state envelope (`signTransaction`/`verifyTransaction`), both HMAC-SHA256 over a base64url JSON body. Sessions are **stateless by necessity**: Cloud Run scales past the one warm instance and an in-memory store would drop them.
- **`routes/auth.ts`** (`/api/auth`) — `GET /login` (302 to Google, `state` + PKCE in a 10-min cookie), `GET /callback` (state check → token exchange → ID-token claim validation → allowlist → session cookie → 302 to the SPA; failures redirect to `/?auth_error=<reason>`, `forbidden` being the not-on-allowlist case), `GET /me` (**public**; returns `{authEnabled, authenticated, user}` — 200 with `authenticated:false` when logged out, never 401, since this is how the SPA discovers its own state), `POST /logout`. **No `google-auth-library`**: the ID token arrives over TLS straight from Google's token endpoint, which is the documented case for skipping JWKS verification, so claims (`aud`/`iss`/`exp`/`email_verified`) are checked directly.
- **`index.ts`** — the codebase's **first and only `onRequest` hook** (there were zero `addHook`/`preHandler`/`decorate` calls before). No-ops when auth is disabled, lets `/api/auth/*` through, else 401. The allowlist is re-checked **per request**, not just at sign-in, so removing an address revokes live sessions. CORS is no longer a bare `register(cors)` — it is an origin allowlist with `credentials: true`; `ALLOWED_ORIGINS` overrides the built-in list.
- **Cookies**: `vt_session` (30d) and `vt_oauth_tx` (10min), both `HttpOnly; SameSite=Lax; Path=/`. **Lax, not Strict** — Strict would drop the cookie on the top-level redirect back from Google. `Secure` is derived from `OAUTH_REDIRECT_URI` being `https://` so local dev over http still works.
- **The redirect URI points at the FRONTEND origin** (`https://<frontend>/api/auth/callback`), not the backend: nginx reverse-proxies `/api/` so the callback still runs in Fastify while the browser stays on the SPA origin, which keeps the session cookie first-party.
- **`OAUTH_REDIRECT_URI` is a COMMA-SEPARATED LIST, one entry per hostname the app answers on** — Cloud Run serves this service at both `…-olncevthqa-an.a.run.app` and `…-839843597381.asia-northeast1.run.app`, and `vt_oauth_tx` is origin-scoped, so starting the flow on one host and being returned to the other loses the cookie and fails the state check with `auth_error=state_mismatch`. `routes/auth.ts:resolveRedirectUri` picks the entry matching the incoming host (unknown host → `[0]`, the canonical one), and the chosen URI is carried **inside the signed transaction** because the token exchange must replay it byte-identically. Every entry must also be registered on the OAuth client in the Console.
- **`nginx.conf.template` must set `X-Forwarded-Host $host`** — it also sets `Host $proxy_host`, which rewrites Host to the backend hostname, so that header is the only surviving record of the public host. Removing it silently breaks multi-host sign-in. The backend never infers the URI from `Host`.
- **Config changes need a restart**, since it is read at boot: `./deploy.sh … --auth` migrates *and* rolls a new revision, which is why they are one flag.
- Both Cloud Run services stay `--allow-unauthenticated`; the app-level hook is the only thing protecting the directly-reachable backend URL.

### Backend (`backend/src/`)
- **Routes** (each is a `FastifyPluginAsync` registered under `/api`):
  - `routes/auth.ts` — see the Authentication section above.
  - `routes/vocab.ts` — smart-add always asks LLM for all four codes (`en`/`ja`/`ko`/`zh`) — `ALL_DEFINITION_LANGUAGES` is hardcoded (lives in `exampleTranslations.ts` with `LANGUAGE_TO_ISO`); request body languages are anchors only. **Before storing, the word's OWN language code is deleted from both `definitions[].text` and every example `translation`** (a same-language gloss is redundant), so a Chinese word persists `en`/`ja`/`ko` only — four are requested, three are saved. Words added before `b7e81ac` (2026-04-08) predate that strip and still carry the source-language definition, so the corpus is mixed. Empty example translations (chip adds send `""`) are normalized to `null` before the LLM call, and any example doc still empty after the merge is LLM-filled via `exampleTranslations.ts:generateMissingExampleTranslations` — shared by vocab POST/PUT and grammar's `resolveExamplesToIds`. Chinese levels normalized at storage time by `CHINESE_LEVEL_NORMALIZE`. Word-group ordering is persisted through `PUT /api/vocab/:language/groups/order`, whose `groupIds` body must contain every group for that language exactly once. **Word drafts**: `word_drafts` Firestore collection + CRUD under `/api/vocab/:language/drafts` (bulk POST assigns `id`/`createdAt` server-side; NO LLM at upload) — mirrors `grammar_drafts`. `WordList`'s "Upload JSON" button ingests `word-drafts` files (format: `docs/draft-json-format.md`). Draft examples may carry `segments: string[]` (chip segmentation — plain segment texts, NOT the `Example.segments` object shape); the review prefill re-inserts spaces at those boundaries (`spaceSentenceBySplits`) so the Chinese chip workflow picks them up and `buildPayload` re-emits them as smart-add `userSplits`. Review flow (mirrors grammar): drafts panel in `WordList` → `SmartAddWordModal` opens with `initialItem`/`initialGroups`/`draftId` prefill and TWO actions — "Save Draft" (form submit / Enter; `onDraftSave` → `PUT /drafts/:draftId`, writes edits back WITHOUT promoting) and an explicit "Register" button that ENQUEUES into the shared word queue (`enqueue` opts `{groupNames, draftId}`: worker creates missing draft groups under the module-level group lock and deletes the draft only after full success — a failed registration keeps the draft) and closes the modal immediately. In-flight drafts show a "Registering…" badge (via `pendingDraftIds`, threaded Dashboard → BrowseView → WordList) with Review/Discard hidden. **Drafts carry NO group data** (removed from the JSON format and both draft types): the drafts panel header has a group `<select>` — defaulting to the most recently CREATED group (`types.ts:latestWordGroup`, by `createdAt`; a user pick sticks until the language changes) — that supplies the target for both the per-row one-click "Register" button (`handleRegisterDraft` builds the smart-add payload straight from the draft, Chinese `segments` → `userSplits`, and enqueues with `{draftId}` so the queue deletes the draft only on full success) and the review modal's preselected group chip (`initialGroups`). A legacy `groups` field in an uploaded file or a direct POST is dropped. Fallback without `onQueue`: direct smart-add await where `onSave` (success-only) is the delete-draft signal.
  - `routes/quiz.ts` — `POST /start` accepts `groupWeights?: Record<string,number>` and `flaggedOnly?: boolean`. When `groupIds` are provided, questions are ordered by `weightedInterleave` (proportional to per-group weights, default 1) instead of `randomSample`; `randomSample` is still used for ungrouped sessions. Resume re-applies weights via `reweightUnanswered` (not a plain shuffle). `PUT /session/language/:language/weights` changes `groupWeights` MID-SESSION: it reorders the unanswered tail with the new weights and returns the full session (questions are SLIM — `slimQuestions` is all Firestore holds) — `QuizTaking`'s "⚖ Adjust Weights" panel re-syncs its local order from the response and jumps to the first unanswered question; the payloads come from its own cache, so a reorder costs no network. **Hydration is BY ID, not by session position** (`POST /hydrate/:language`, body `{wordIds}` → `{questions}`): a session's order changes constantly (retry re-queues, resume reweighting, weight edits) while the SET of ids never does, so an id-keyed client cache makes every reorder free. The endpoint needs no session, so the word, Group A and Group B quizzes all share it — there is no per-quiz `/questions/:language` any more, and no `BATCH_SIZE` paging. `POST /start` still returns lightweight `{wordId, term}`. Wrong answers call `insertRetryQuestion` server-side, which splices the missed word into the tail — `score.total` grows accordingly; the client applies the same mutation locally (see the offline section under **Frontend**) and does not wait for the response.
  - `routes/grammar.ts` — `Grammar` has `statement` + `descriptions: Meaning[]` (mirrors `Word.definitions`). Examples are normalized into the shared `example_sentences` collection via `exampleIds[]` (mirrors `Word.exampleIds`); inline `Grammar.examples` is a transitional fallback for unmigrated docs. POST/smart-add/PUT resolve incoming `examples` to existing or new `example_sentences` docs via the sha256 dedup index (so a sentence shared with a vocab word gets one doc) and `addGrammar`/`updateGrammar` keep `ExampleSentence.appearsInGrammarIds` in lockstep using a Firestore batch. PUT delete-cascades dropped examples through `isExampleReferencedByAny` (cross-domain check covering both `Word.appearsInIds` and other `Grammar.exampleIds`). User-curated `grammar_groups` collection mirrors `word_groups` — per-language, owns membership via `grammarIds[]`. CRUD lives under `/api/grammar/:language/groups`. `POST /:language/smart-add` LLM-enriches `descriptions[].text` to all four ISO codes (mirrors vocab smart-add); `GrammarFormModal` create path uses smart-add, edit (PUT) stays manual. **`Grammar.transliteration` (statement pinyin) is generated for Chinese at EVERY write path** — the local `resolveTransliteration` helper is called from `POST /items`, `POST /smart-add` and `PUT /items/:id` alike (in parallel with `resolveExamplesToIds` on the two creates), so "a stored Chinese grammar item has a reading" holds no matter which route the caller used. It exists because only `GrammarFormModal` ever had an INPUT for the field, so every queue-driven create (article import above all, which is what feeds Group B) stored Chinese grammar with no reading and the quiz reveal had nothing to show. The helper NEVER overwrites: a supplied or already-stored value is returned untouched, which is what makes it safe on PUT — an edit fills a missing reading but cannot clobber a hand-tuned one (`undefined` is dropped by `ignoreUndefinedProperties`, leaving the stored value alone). A failure logs and stores without it rather than sinking the write.

`llm.ts:fillGrammarTransliteration` does the work, and its alignment guarantee is **structural, not prompted**. A statement is pattern notation, so `splitStatementForReading` (exported, pure) cuts it in code into maximal CJK / non-CJK runs; only PURE-HAN runs are sent to the model (a run holding any kana is Japanese annotation — 「状態を表す述語」 — and is kept verbatim), and the result is reassembled here. Placeholders, connectors and spacing therefore never reach the model and cannot be dropped: the earlier whole-string prompt silently ate the leading `s+` of 「s+使役動詞+人/もの+v」 and truncated 「s+被/让/叫+行為者+v+結果補語」 to just "bèi/ràng/jiào". The model's only per-run decision is "Chinese → pinyin" or "Japanese grammatical term (程度副詞/可能補語/使役動詞) → empty", judged with the full statement as context. A statement where nothing came back Chinese yields NO reading rather than an echo of itself (an echo prints the quiz prompt twice). Tone marks are mandatory — `llm.ts:toneMarkNumberedPinyin` deterministically rewrites any numbered pinyin that slips through (`hao3` → `hǎo`, `de5` → `de`, `lv4` → `lǜ`), mirroring `PinyinInput.tsx`'s typing rule. `GET/PUT /api/grammar/settings` persist `GrammarSettings { defaultDefinitionLanguage }` in Firestore doc `config/grammar_settings` — seeds the first description row in `GrammarFormModal` (module-level `cachedDefaultDescLang` avoids the fetch race on repeat opens). Grammar example translations pass through as-is (`string | Record<string,string>`): `hydrateGrammarItems` no longer coerces multi-lang objects to a single string; the UI renders them via `displayGrammarDefEntries`. Config in Firestore `config/grammar` (local source `backend/DB/grammer/config/`, pushed by `migrate-db-config-to-firestore.ts --prompts`). **Grammar drafts**: `grammar_drafts` Firestore collection + CRUD under `/api/grammar/:language/drafts` (bulk POST assigns `id`/`createdAt` server-side; NO LLM at upload). Drafts hold raw inline `examples` — never normalized to `example_sentences` until promoted. Sources: the local OCR tool (`~/workspace/textbook_content_extractor/server/`, separate repo, NOT deployed) posts directly, and `GrammarList`'s "Upload JSON" button ingests `grammar-drafts` files (format spec: `docs/draft-json-format.md`, which also pre-defines the future `word-drafts` format). Review flow: drafts panel in `GrammarList` → `GrammarFormModal` opens in create mode via its `initialItem` prop (prefill-only; `isEdit` stays keyed to `editItem`) with TWO actions: "Save Draft" (the form submit / Enter; `onDraftSave` prop → `PUT /drafts/:draftId`, writes edits back WITHOUT promoting — Chinese sentences keep user-typed spaces so chip splits survive the round-trip) and an explicit "Register" button that ENQUEUES into the shared grammar queue and closes the modal immediately so the next draft can be reviewed. `useGrammarQueue.enqueue` takes optional `{groupNames, draftId}`: the QUEUE worker attaches group names (created if missing, serialized via a module-level lock so parallel workers don't duplicate a new group) and deletes the draft only after full success — a failed registration keeps the draft. When a create has no `groupNames` (or `initialGroups`, on the non-queue fallback path), it defaults to the most recently created group for that language (`types.ts:latestGrammarGroup`, by `createdAt`) instead of staying ungrouped; a language with zero groups yet stays ungrouped. In-flight drafts show a "Registering…" badge (via `grammarPendingDraftIds` + legacy `grammarPendingTerms`, threaded Dashboard → BrowseView → GrammarList) with Review/Discard disabled. **Drafts carry NO group data** (mirrors words): the drafts panel header's group `<select>` (default = `latestGrammarGroup`, a user pick sticks until the language changes) feeds both the per-row one-click "Register" button (`handleRegisterDraft` → `onGrammarQueue(..., {groupNames, draftId})`, Chinese space-splits → `userSplits`) and the review modal's `initialGroups`. A legacy `groups` field in an uploaded file or a direct POST is dropped. Fallback without `onGrammarQueue`: direct smart-add await where `onSave` (success-only) is the delete-draft signal.
  - `routes/grammar-quiz.ts` — `/start` accepts `groupIds` to scope the pool (no chapters/subchapters/displayLanguage/quizMode). Without an explicit `questionCount` the session covers the **ENTIRE** matching pool (`count = pool.length`, mirroring `routes/quiz.ts`; it used to cap at 10, which silently sampled down a selected group) — so `groupWeights`/`correctWeight` only decide the ORDER of the questions, never which items make the cut. A bucket weighted `0` is still dropped outright by `weightedMerge`, which is how "exclude this group / exclude already-correct items" works. Questions are flashcard-style: `GrammarQuizQuestion` carries only `{grammarId, statement}` — the statement IS the prompt; the client bulk-fetches the full items (`POST /api/grammar/:language/items/batch`, hydrated examples included) and reveals descriptions + registered examples on answer. No LLM at question time. Resume (`GET /session/language/:language`) re-draws the unanswered tail via `reweightUnansweredGrammar` — it used to be a bare passthrough, the only one of the three quizzes that did not regenerate on resume. Retries are **appended** here (`questions.push`), NOT spliced into the tail like the word/combined quizzes — `utils/quizLocal.ts` mirrors that difference deliberately. Also exposes `check-missing-words` and `add-missing-words` (currently unused by the UI after the quiz simplification).
  - `routes/import.ts` — `POST /api/import/:language/analyze-stream`, SSE-over-POST (same transport as `routes/translation.ts`). One FULL-model streaming call splits an article into paragraphs/sentences and extracts words + grammar points; `paragraphs` is the schema's first key so the client can live-render sentences from the partial stream (`api/import.ts:extractStreamingSentences`). Sentence indices are assigned SERVER-side by position (schema omits them, mirroring `ensureDecompositionIds`) and out-of-range extractions are dropped. Existing grammar `statement`s are injected as style examples. **The analysis is EXHAUSTIVE, not selective**: `backend/DB/import/system_prompt_analyze_*.md` ask for complete per-sentence segmentation — every letter/ideograph of a sentence must belong to exactly one `words` entry (function words, particles and measure words included; only punctuation, spaces and digits are left out), listed in sentence order, once per sentence per distinct term but AGAIN for every sentence the term appears in, since each sentence has to be covered on its own. `term` is the SURFACE form (a verbatim substring of the sentence) so the client can match it back positionally — this is why the prompts no longer ask for the dictionary form. **`transliteration`/`meaning` are written ONCE per term, on its first occurrence in the article; every later occurrence returns `""` for both** and `normalizeAnalysis:backfillRepeatedWords` (exported, unit-tested) fills them in — FIRST wins, not last, and the two fields inherit independently, since the model routinely blanks one and not the other. The prompts carve out an explicit exception for a genuinely different reading or sense (多音字 还 hái/huán, 了 le/liǎo; Japanese 行った itta/okonatta; English "lead"/"read"), which must still be spelled out — without it polyphony would collapse onto the first reading. Consequence: output volume scales with article length, so `normalizeAnalysis` reports a truncated response as an over-long-article error instead of a bare JSON parse failure, and `ImportView` warns past `LONG_TEXT_WARNING` (1500 chars) — `MAX_TEXT_LENGTH` stays 8000 but is no longer realistically reachable in one call. The server only analyzes + existence-checks; **registration is entirely client-side** through the existing word/grammar queues, so there is no new write path. The `analysis-result` event carries TWO existence maps: `existing` (term → word ID, via `lookupWordsByTerms`) and `existingGrammar` (normalized statement → grammar ID), the latter built from the `getAllGrammarItems` call the style examples already need, so it costs no extra read. Grammar smart-add still has no server-side duplicate check (`reply.conflict` exists only in `routes/vocab.ts`, so a grammar 409 is unreachable) — de-duplication is the client's job via `existingGrammar` plus sibling propagation. UI: `ImportView.tsx`, reached as the third tab of `BrowseView` (see below). **Import sessions**: the same file also serves CRUD for `import_sessions` under `/:language/sessions` (nested under `:language` to match the drafts convention and stay clear of `/:language/analyze-stream`) — `GET` (returns `{sessions: ImportSessionSummary[], pool}` — projected summaries, never the full items array), `POST` (201, server assigns `id`/`createdAt`/`updatedAt`), `GET/PUT/DELETE /:sessionId`. **The `pool` on that GET is the article quizzes' question set**: the deduped union, across every saved session of the language, of `existingWordId`/`existingGrammarId` on non-`skipped` items. It rides along with the list rather than living on its own endpoint because this handler ALREADY reads every session document in full, so a sibling route would re-read the same heavy docs on one screen load (the same consolidation `useImportGroups` makes on the client). **Which item went to Group A vs Group B is deliberately NOT decided here** — the session records a *destination* (`wordGroupId`/`grammarGroupId`/`groupBNames`, all freely mutable mid-review) and never per-item membership, and `ImportItem.target` is last-write-wins (a B press on a new entity writes the A group too), so A/B is reconstructed client-side by intersecting these ids against the group documents `ImportView` already holds. `utils/importQuizPool.ts:deriveArticleQuizPools` is that split, and it is **asymmetric on purpose**: Group A is the pool UNCHANGED (every id came from an item with an entity id, so it is in the library, and `utils/importSession.ts:registeredTerms` already states that "in the library" and "in Group A" are the same thing for import material — intersecting would silently drop a word in no group, and empty the A quiz entirely for a language with no category-A groups yet), while Group B IS intersected, because there the membership is the meaning and "nothing marked B" is a correct empty answer. B is therefore a subset of A, not a peer. PUT is the autosave target and re-stamps `updatedAt`; `items` replaces wholesale so deleted/merged rows actually disappear. Collection schemas are loose (`items: {type:"array"}`) because a deep JSON schema fights the `ImportItem` discriminated union.
  - `routes/combined-quiz.ts` — merged word+grammar quiz at `/api/combined-quiz`. **UI naming**: surfaced to the user as "Group A Quiz" (paired with the Group B quiz); ALL code/route/i18n-key identifiers keep the `combined` name (`combinedQuiz`, `startCombinedQuiz`, `resumeCombinedQuiz`, `selectCombinedFilters`, route `/combined-quiz`) — only the displayed i18n string *values* were changed to "Group A". Two-level weighted ordering: each domain is ordered internally by group weights (`weightedInterleave`; grammar groups gain weights here — the standalone grammar quiz has none), then the two streams are merged by `domainWeights: {word, grammar}` via `weightedMerge` (order-preserving draw; a weight of 0 skips that domain). Questions are a `kind`-discriminated union (`CombinedQuizWordQuestion | CombinedQuizGrammarQuestion`); `/answer` takes `{kind, refId}` and dispatches to word vs grammar progress + retry re-queue. Word questions hydrate through the shared `POST /api/quiz/hydrate/:language` (this file has NO hydration endpoint of its own — the word payload is identical); grammar questions are tiny (`{grammarId, statement}`, same flashcard format as the standalone grammar quiz) and stored inline, with descriptions/examples fetched in bulk via `POST /api/grammar/:language/items/batch`. Sessions live in `combined_quiz_sessions` keyed by language; resume (`GET /session/language/:language`) reweights the unanswered tail per-domain then re-merges (shared `reorderUnansweredTail` helper). `PUT /session/language/:language/weights` changes `domainWeights`/`wordGroupWeights`/`grammarGroupWeights` MID-SESSION via the same helper and returns the full session — `CombinedQuizTaking`'s "⚖ Adjust Weights" panel re-syncs from the response; at least one domain weight must stay positive (a 0-weight domain's remaining questions are appended at the end, not dropped). Shared ordering helpers (`shuffle`/`weightedInterleave`/`weightedMerge`/`insertRetryQuestion`) live in `src/quiz-utils.ts`, also used by `routes/quiz.ts`. **Group B, mixed A+B and the two article quizzes**: the plugin is a factory `makeCombinedQuizRoutes({ sessionKey })` registered **FIVE** times — `/api/combined-quiz` (key = `language`), `/api/group-b-quiz` (key = `` `${language}__groupB` ``), `/api/mixed-quiz` (key = `` `${language}__mixed` ``), `/api/import-quiz-a` (`` `${language}__importA` ``) and `/api/import-quiz-b` (`` `${language}__importB` ``) — so all five sessions coexist in `combined_quiz_sessions` for one language and starting one never disturbs another. `getCombinedQuizSession` takes the doc key (not the language) and `saveCombinedQuizSession` keys off `session.sessionId`; `session.language` stays the plain language for client API calls. The B and mixed variants send no `flaggedOnly`. **The handlers never read the meta-group `category` field** — they resolve group docs by id only and never inspect `WordGroup.category`/`GrammarGroup.category`. (The `categories` occurrences in this file are the unrelated part-of-speech filter.) A vs B is decided entirely client-side by which `groupIds` get sent, which is why the mixed quiz needed no new handler logic — it just sends both categories in one array. **Explicit-id pools + `randomOrder`** (both added for the article quizzes): `word.wordIds` / `grammar.grammarIds` on `/start` REPLACE the pool query outright — `getWordsByIds` / `getGrammarItemsByIds` instead of `getFilteredWords` / `getAllGrammarItems`, which is cheaper than the filter path, not dearer, and drops ids whose document has since been deleted rather than erroring. An empty array means an empty pool (an empty array is truthy), NOT "the whole language". `randomOrder: true` replaces the final `weightedMerge` with ONE `shuffle` of the union and is stored on the session so `reorderUnansweredTail` shuffles the tail on every resume too; `PUT …/weights` rejects such a session. It exists because **`weightedMerge` at 1:1 is not a uniform shuffle** — it picks a BUCKET per draw, so with 200 words against 20 grammar items every grammar card lands in the first ~40 positions. Zero-weight buckets are still excluded under `randomOrder`: randomness is about order, not membership. Frontend: `api/combined-quiz.ts` takes a `variant?: "combined" | "groupB" | "mixed" | "importA" | "importB"` on all five functions, resolved through a **total `Record` map** (`VARIANT_BASE`) rather than an if-chain, so a variant added to the union without a path is a compile error instead of silently posting answers into the plain Group A session; `CombinedQuizFilterModal` takes `groupCategory`/`showFlaggedToggle`; `CombinedQuizTaking` takes `variant`, where the "3" key becomes "remove from all Group B groups" for BOTH kinds (local badge only — the item stays in the running session) under `usesGroupBControls = variant === "groupB" || variant === "mixed"` — the plain Group A quiz and BOTH article quizzes bind "3" to flagging instead, and the two Group-B-aware variants skip the flagged-ids fetch entirely. The ⚖ weights control is gated on `!session.randomOrder` (keyed off the session, not the variant, so it is self-describing).

  **The mixed A+B quiz** (`/api/mixed-quiz`, UI "Group A+B ミックスクイズ", **Chinese only** — gated by `isoCode === "zh"` in `EmptyState.tsx`, inside the existing `showGrammar` block) exists because Group B is by definition a SUBSET of Group A, so neither existing quiz could express "drill this week's lesson with my weak words mixed in thicker". Two client-side mechanisms carry it, both in `frontend/src/utils/quizGroupScope.ts` (pure, mirrors the `utils/weightInput.ts` split):
  - **`scopedGroups(groups, "AB")` lists category B FIRST**, and that order is load-bearing rather than cosmetic. `getFilteredWords` unions the selected groups' `wordIds` so the pool has no duplicates, and `assignMembership` gives each item to the FIRST group in `groupIds` order that holds it — so B-first is precisely what makes a word sitting in both an A lesson and a B study set count against B's weight. Consequently `buildFilters` emits `groupIds` in **list order, not Set-iteration order**: unchecking and rechecking a group moved it to the end of the `Set` and silently broke the B-first rule.
  - **`applyCategoryRatio` folds the A↔B ratio into the per-group weights**, because the backend weights buckets per GROUP, not per category. Scaling each side by the OTHER side's weight-sum (`a_i * wA * S_B` vs `b_j * wB * S_A`) lands on the requested ratio **without dividing**, so integer inputs stay integers for `scaleWeightRecord` to GCD-reduce. A category with nothing selected scales by 1, not 0, which would otherwise zero the whole domain. This is worth a helper because the correct per-group number is not one a user would guess: five A groups against one B group at 1:3 gives the B group weight **15**, and it changes every time a checkbox is ticked.

Off passes `segments={undefined}` to `RubyText` (which then renders plain text) and drops a grammar example's whole-sentence `transliteration` line. The button is omitted where there is no reading to hide (`hasExampleReadings`), so it never appears on Japanese or Korean. It does NOT touch the definition pinyin or `GrammarDescriptionsPanel`'s statement pinyin — those are the answer, not the example.
  - `routes/expressions.ts` — CRUD + group management for `Expression` items at `/api/expressions/:language`. No LLM; fully user-curated. Mirrors grammar pattern (`expression_items`/`expression_groups` collections).
  - **There are TWO expression quizzes.** `routes/expression-quiz.ts` is the **writing** one: you compose a sentence and an LLM corrects it. `routes/expression-recall-quiz.ts` is the **recall** one (flashcard, no LLM at all).

Its own `expression_recall_sessions` collection (doc id = language), a real sub-path `/:language/expression-recall`, and the same shape as `routes/grammar-quiz.ts`: without an explicit `questionCount` the session covers the **entire** matching pool (weights decide ORDER, never who makes the cut), ordering is `weightedInterleave` when `groupIds` are given and `shuffle` otherwise, resume re-draws the unanswered tail, and **retries are appended, not spliced** (matching grammar; `utils/quizLocal.ts` mirrors whichever applies). `direction` (`"phrase-to-context"` default, or `"context-to-phrase"`) picks which face is the prompt and is stored on the SESSION; the prompt text is **denormalized onto each question** so a card renders before hydration lands — which also means a mixed-direction mode isn't representable, and editing an expression mid-session leaves the stored prompt stale (`GrammarQuizQuestion.statement` has the identical property). `purposeFilter` keeps the writing quiz's rule that an expression with no `purpose` matches every filter. **No `expression_progress` / SRS / "already-correct" bucket** — expressions carry no progress data at all.

Two-step: decompose (MINI, source-lang prompt) → translate (FULL, target-lang prompt). Output uses `passages[].{ sentenceIds[], translation }` — LLM may group consecutive sentences. `buildTranslateSystemPrompt` appends source/target + approach guidance + optional user `context` (situation/register hint, persisted on `TranslationEntry.context`) to the Firestore prompt without needing a migration — context must stay LAST so the static prefix keeps hitting OpenAI prompt caching. The API key and the two tier defaults come from `.env` (local) or Firestore `config/llm` (deployed), resolved once and memoized forever by `ensureInit`. **Per-feature model assignment** sits on top of that: every one of the seven calling functions already took a trailing `route` label (it exists for `recordUsage`'s per-feature token accounting), and `llm-features.ts` reuses those exact labels as configuration keys — which is why per-feature models needed **no change at any of the ~20 call sites**, only a one-line swap of `getModelMini()`/`getModelFull()` for `resolveModel(tier, route)` in each of the seven. `LLM_FEATURES` groups the 17 route labels into 12 user-facing features (a stream and non-stream variant of one job share a row); a route that isn't listed — the `scripts/*` ones, `"unknown"` — falls through to the tier default.
  - **Resolution order**: `config/llm_models.features[featureKey]` → `config/llm_models.defaults[tier]` → the env / `config/llm` value. This **inverts** `loadLLMConfig`'s "env always wins" rule, and only for model *names*: per-feature assignment has no env equivalent, and a settings screen whose saved value silently does nothing is broken. It can only ever affect a local dev — `deploy.sh` sets exactly one env var on Cloud Run (`FIRESTORE_DATABASE_ID`), so in production there is no competing env value at all.
  - **`config/llm_models` is read through a 30s TTL cache, NOT memoized like `initPromise`.** The settings screen writes it at runtime and Cloud Run runs several instances, so invalidating only the instance that served the PUT would leave the others on the old model until the next deploy. `invalidateModelConfigCache()` (called by `PUT /api/llm-config`) makes the writing instance instantly consistent; everyone else catches up within 30s. `readModelConfig` **never throws** — seven code paths now depend on a Firestore read that previously wasn't in the picture, so a blip degrades to the last known value, then to env. A single in-flight promise is shared so the `CONCURRENCY=4` smart-add queue doesn't fire four reads the moment the TTL lapses.
  - `ensureInit` now nulls `initPromise` on rejection. It used to cache the failure for the process lifetime, so a first call made before the config was reachable kept rethrowing the same stale error even after the config was fixed.
- **`routes/llm-config.ts`** (`/api/llm-config`) — `GET /` (assignments + `effective` model and `source` per feature + the env `tierFallbacks`; **structurally cannot leak `OPENAI_API_KEY`**, which lives in a different document), `PUT /` (rejects unknown feature keys rather than storing config the UI could never display or clear), `POST /test` (two probes — `models.retrieve` answers "does this name exist" on its own, since a failed completion alone can't distinguish a bad name from rejected parameters; the provider's error text is returned verbatim, and a successful test calls `ensureModelInCostConfig` so the model shows up on the Costs tab immediately), `GET /available` (`models.list()`, unfiltered and newest-first — filtering by name prefix would reintroduce hardcoded model knowledge, which this repo has none of). `/test` deliberately bypasses `recordUsage`: a settings probe is not study activity.

Backend routes (`vocab.ts`, `grammar.ts:resolveExamplesToIds`) feed `userSplits` to `fillSegmentPinyin` + `lookupWordsByTerms` to produce `example_sentences.segments` with word IDs. `GrammarExample.userSplits` is input-only — never persisted.

### Data Storage
- **Firestore** (database ID: `vocab-database`). Key composite keys: `progress`/`word_index` use `{language}_{wordId}`, `example_sentence_index` uses `{language}_{sha256(sentence).slice(0,16)}`.
- `example_sentences` — normalized; words store `exampleIds` and `appearsInIds` arrays referencing this collection. **Grammar items also reference this collection** via `grammar_items.exampleIds[]`; the reverse link is `ExampleSentence.appearsInGrammarIds[]`. A sentence shared by a word and a grammar item resolves to ONE doc via the sha256 dedup index. Orphan deletion (in `deleteWord`, `deleteGrammarItem`, and the vocab/grammar PUT routes) MUST use `isExampleReferencedByAny` so vocab deletes don't clobber grammar-owned examples (and vice versa). `validate-invariant-all.ts` enforces the bidirectional invariant `ES.appearsInGrammarIds == { gId | grammar(gId).exampleIds ∋ ES.id }`.
- `config` subcollections: `config/llm`, `config/llm_models`, `config/auth`, `config/token_costs`, `config/speaking_writing`, `config/translation`, `config/vocabulary`, `config/grammar`, `config/grammar_settings`, `config/import`
  - `config/llm_models` fields: `catalog` (registered model names), `defaults` (`{mini?, full?}`), `features` (featureKey → model name), `updatedAt`. **UI-owned, and deliberately NOT part of `config/llm`** for two reasons: `migrate-llm-config-to-firestore.ts:52` does a full `.set()` on `config/llm`, so anything stored beside the API key would be wiped by the next `./deploy.sh --llm`; and keeping the key in a separate document means `GET /api/llm-config` structurally cannot leak it. Created by the first save from the UI — there is no migration script and `deploy.sh` is untouched.
  - `config/auth` fields: `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `OAUTH_REDIRECT_URI`, `SESSION_SECRET`, `ALLOWED_EMAILS` — see the Authentication section. **The doc's absence is meaningful**: it is the signal that auth is off.
  - `config/import` fields: `analyzeSchema`, `analyzePrompts` (keyed by backend language NAME) — local source in `backend/DB/import/`; push with `migrate-db-config-to-firestore.ts --prompts`. `routes/import.ts` loads it LAZILY so a missing doc can't stop the server from booting.
  - `config/translation` fields: `decomposeSchema`, `decomposePrompts`, `translateSchema`, `translatePrompts` — local source in `backend/DB/translation/`; push with `migrate-db-config-to-firestore.ts --prompts`
- `import_sessions` — one paused, resumable article review each (auto-ID docs with a `language` field, listed by an in-memory `updatedAt` sort to avoid a composite index — the `translation_history` pattern, NOT the singleton-per-language quiz/speaking pattern, since several articles can be in progress at once). Holds `paragraphs` + the flattened `items` working copy + destination groups; see the `ImportView.tsx` entry below for the item model.
- `expression_items`, `expression_groups` — per-language, mirror the grammar collection structure. Note expressions are keyed by **ISO code** (`"en"`), whereas words and grammar use the full-name URL segment (`"english"`) — the expression components are passed `isoCode`, and passing `language` instead yields an empty pool with no error. `ExpressionQuizSubsession` (the writing quiz) is NOT a separate collection; it is stored as `SpeakingWritingSession.expressionQuiz?` in `speaking_writing_sessions`.
- `expression_recall_sessions` — the **recall** quiz's own collection (doc id = language code). Separate from `speaking_writing_sessions` on purpose: see the co-tenancy note under `routes/expression-quiz.ts`.
- **Meta-groups (`category`)**: `word_groups`/`grammar_groups` docs carry an optional `category?: "A" | "B"`. **Absent = "A"** and only `"B"` is ever written, so every pre-existing group is Group A with zero migration. "A" is the universe of all items (every existing flow — drafts, chips, browse filters, word/grammar/combined quiz setup — filters to A via `types.ts:categoryGroups`); "B" is the not-yet-memorized subset drilled by the Group B quiz. `latestWordGroup`/`latestGrammarGroup` reduce over category A only, so a B group is never an implicit default. Group B membership is added on top of A by the shared `GroupBSelect.tsx` chips (every add flow assigns an A group, which is what upholds "a B item is always also in A" — there is NO server-side validation; the importer's Group B button keeps it by writing the A destination too whenever it has to create the item). **A Group B group spans both domains**: unlike Group A, where a word group and a grammar group are unrelated sets, one Group B study set holds words AND grammar. It is still stored as two docs (one `word_groups`, one `grammar_groups`, both `category: "B"`) joined by NAME — `frontend/src/utils/groupB.ts` (`UnifiedGroupB`, `loadGroupBGroups`, `createGroupBGroup`, `resolveGroupBTargets`) is the merge/create/resolve layer, and `GroupBUnifiedSelect.tsx` is the name-keyed picker built on it (with inline "new group" creation, which creates both sides at once). `resolveGroupBTargets` only materializes the side a registration actually needs, so importing an article with no grammar never leaves an empty grammar group behind. The per-domain `GroupBSelect.tsx` stays in use by the single-domain add forms. Category is fixed at creation (no PUT). `firestore.ts:removeWordFromCategoryBGroups` / `removeGrammarFromCategoryBGroups` back `DELETE /:language/group-b/members/:id` on both vocab and grammar. **Reorder invariant**: `PUT /vocab/:language/groups/order` still requires EVERY group of the language exactly once, so `GroupPickerModal` appends the hidden category's IDs after the visible reordered ones.
- `word_groups` — per-language groups own membership through `wordIds[]` and may carry numeric `order`. `getWordGroups` sorts by `order`, with creation time as the legacy fallback. The first reorder operation backfills a complete zero-based order for all groups; new groups append to an ordered list.
- **Category A is EXCLUSIVE for words**: a word belongs to at most ONE category-A word group, so adding it to one is a **MOVE** — `firestore.ts:modifyWordGroupMembers` calls `removeWordsFromOtherCategoryAGroups` after the add. The A groups are the lesson structure, a partition of the library rather than overlapping tags, so a word that reappears in a later lesson belongs to that lesson only. **Grammar is NOT subject to this** (a grammar item may still sit in several A groups), and category B never is — a B group is the not-yet-memorized subset drawn on top of A and several may hold the same word. The removal runs OUTSIDE the caller's transaction (mirroring `removeWordFromCategoryBGroups`): Firestore wants all of a transaction's reads before its first write, while "which other A groups hold this word" is only knowable after the target doc has been read; losing the race leaves a word in two groups, which the next add repairs and `scripts/dedupe-word-group-membership.ts` sweeps. Every add path in the app funnels through this one function, which is why no caller has to cooperate — but the pickers were made honest anyway: the Group A chips in `WordFormModal`/`SmartAddWordModal` are **single-select**, and `GroupPickerModal.handleAddToGroup` re-reads the collection after an add (patching one group locally would leave the source group's count stale).
- **Local files**: `backend/DB/` (grammer, speaking&writing, translation, vocabulary, backup, old, original). Word JSON is no longer mirrored locally — Firestore is the source of truth; `old/` and `original/` hold pre-migration HSK archives.
- **Docs**: `docs/draft-json-format.md` (draft upload format) · `docs/word-grammar-crud.md` (Word/Grammar storage model, Group A/B semantics, the full CRUD route table, and the 2026-07-29 live verification report — including the known gap that `deleteWord`/`deleteGrammarItem` do NOT strip the id from `word_groups.wordIds`/`grammar_groups.grammarIds`, so group member counts drift upward).

All language codes use ISO 639-1: `ja`, `en`, `ko`, `zh`. The export script normalizes legacy keys (e.g., `"Japanese"` → `"ja"`, `"kr"` → `"ko"`) on export.

Destination is picked before analysis and stays editable through review (`ImportDestinationRail`: two **Group A** selects defaulting to `latestWordGroup`/`latestGrammarGroup`, plus a **Group B** `GroupBUnifiedSelect`); it applies to items added *from then on*, not retroactively.
    - **Item model** (`utils/importSession.ts`, all pure): the analysis's positional `words[]`/`grammar[]` are flattened once into `ImportItem[]` with stable client ids — the raw arrays are NOT persisted, so there is one working copy and no drift. **A word row's `order` is the term's CHARACTER OFFSET in its sentence**, not its index in the analysis array: array order is only as good as the model's willingness to emit words in sentence order, and offsets are what let a materialized gap row slot into reading order. The nth listing of a term takes its nth occurrence (counted per term — a shared cursor would mis-place every word emitted out of order, which is the case this repairs); a term that is not a substring at all (routine for Japanese/Korean, where the prompts split inflections) gets `previousOrder + 0.001`, a step small enough never to collide with a gap run's integer offset. `order` is still **fractional** so a split inserts its parts between neighbours without renumbering — safe against offsets because `splitWordItem` keeps all parts strictly inside `(o, o+1)` while a term of length L pushes its neighbour to `o+L`. Order is computed at BUILD time only; `undoDerivation` restores the original values. Merge/split/delete **tombstone** their sources (`status:"skipped"` + `supersededByIds`) rather than removing them, which is what makes `undoDerivation` possible and keeps the session a complete record. `mergeWordItems` derives the new term from the sentence SPAN the sources cover (`sentenceSpanForTerms`), not naive concatenation, falling back to concatenation when a term isn't a literal substring; it always drops `meaning` (a compound's gloss is not the sum of its parts). **Readings are merged and split automatically**: `mergeTransliteration` joins the sources' readings whenever the merged term is exactly those sources concatenated (right by construction — no syllable arithmetic can improve on it), and `splitTransliteration` binds one syllable per character. Both go through `readingSyllables`, which prefers whitespace boundaries and falls back to `tokenizePinyin` — a longest-match-with-backtracking cut over a table of every toneless Mandarin syllable, plus the rule that a candidate carrying two tone marks is two syllables (which is what tells 「xīān」 from 「xiān」). Non-pinyin readings (kana, hangul) fail to tokenize and come back `undefined` rather than mis-cut. A reading is dropped only when a source had none, or when the merge spans MORE than its parts (「食べ」+「みる」 over 「食べてみる」) so the joined reading would sit off its characters. Merge has two affordances: the per-row "↓と結合" button (merge with the row below — the common case) and the multi-select checkboxes.

    - **Coverage** (`utils/importSession.ts`: `sentenceCoverage` / `coverageRuns`, pure): the counterpart to exhaustive extraction — which characters of a sentence the live word rows account for. A character is in scope when it matches `\p{L}`; punctuation, spaces, digits and symbols never are, so 「。」 can't hold a sentence back. A term covers EVERY occurrence of itself in the sentence (the prompt lists a repeated word once), found through `termOccurrences`: **a Latin-script term matches only at word boundaries and case-insensitively**, without which the English article 「a」 marks the `a` inside 「analysis」 and coverage is so over-claimed that no English sentence ever reports a gap. CJK terms keep plain case-sensitive substring matching. If a term isn't a substring at all the longest prefix that is covers its FIRST occurrence only — an inflection fallback that never fires for Chinese, and which sets **`SentenceCoverage.approximate`**: that search starts at index 0 rather than where the word belongs, so the covered flags (and the gap runs derived from them) may sit on the wrong characters. **Grammar rows never contribute**: a `statement` is pattern notation (「随着～，越来越～」), not a substring, so it cannot be matched positionally.
      **Gaps become real rows, not just a highlight** (`materializeGaps`): `buildImportItems` runs it over every sentence, so "every word of every sentence is on screen" holds from the moment the review opens rather than depending on the user noticing an amber run. One run = one row (`origin: "gap"`, amber left border, no reading/meaning, a "type a space to split it" hint) — guessing internal boundaries would invent a segmentation nobody asked for, and `splitWordItem` is one keystroke away. It **refuses to act on an `approximate` sentence**, where the runs are a guess; those keep the highlight plus a manual "add the uncovered text as rows" button, which is also how a gap reopened by a later edit is closed. `origin: "gap"` is load-bearing beyond styling: `useImportLibraryStatus` skips `origin === "llm"` rows for `check-terms`, so a gap row — never part of the server's `existing` map — must not claim to be one. `ImportReview` memoizes a `sentenceIndex → missing` map so each collapsed row leads with its gap count; a rescan per render would be O(sentences × items).

The coverage line stays OUTSIDE the pinned area — it is an occasional action, not context — and `max-h-[40vh]` caps a very long sentence plus translation.

Since `position: sticky` anchors to its nearest SCROLLPORT ancestor, that silently made **every sticky in the importer inert** — the pinned sentence, the mobile prev/next bar and the `lg:sticky` destination rail all just scrolled away with the page (the prev/next bar sits at the end of the content, so nobody noticed it had never pinned). It is now `min-h-full overflow-x-clip`: `overflow-x: hidden` promotes the other axis's `visible` to `auto` per the CSS overflow spec and so creates a scrollport all by itself, whereas `clip` is the one value that coexists with `visible` — it stops sideways overflow without establishing a scroll container. The other `ImportView` phases keep the old wrapper; they hold no sticky.

The open/shut flag is LOCAL state in `ImportReview`, deliberately not `focusedSentenceIndex`: that field is session data and required on the wire, so "which sentence" and "open or shut" stay separate rather than smuggling a `-1` into the saved document — prev/next still steps from the folded sentence, which keeps a ring to show it is current. `focusRef` is a callback ref carried by whichever shape the focused sentence has (open card wrapper or collapsed row) and `collapsed` is a dependency of the scroll effect, because folding removes hundreds of pixels from ABOVE the scroll position.     - **Registration is per item AND per destination.** `registerItem(id, target)` writes ONE destination: `"A"` the Group A lesson group, `"B"` the Group B study set — two buttons on every row (`RegisterControls`/`DestinationButton` in `ImportSentenceCard.tsx`), coloured like the destination rail's dots (**A indigo, B amber**) and labelled with the chosen group's NAME plus an A/B badge. One button could not express "already in A, still needs B", the ordinary state of an article that repeats vocabulary the user already owns. A **B press also writes the A destination when the entity does not exist yet** — a Group B group is the not-yet-memorized SUBSET of A, so an item created into B alone would be missing from the browse lists and every Group A quiz — but an item already in the library is left where it is, so pressing B never moves a word out of its lesson. `groupBIdsFor` is therefore resolved only for a B press: it CREATES the missing half of a B set, and an A press has no business materializing one. **The ✓ is read from actual membership** (`GroupMembership.aIds` — group IDs, since the A destination is chosen by ID — plus `b` by NAME, which is how a B set is joined across domains), never from `status`: status is the outcome of the last write this review made, while the question on screen is where the item sits now. `status` only drives the transient states. **Those transient states are PER DESTINATION** — `ImportItemBase.registrations: Partial<Record<"A"|"B", ImportRegistrationState>>` is the real record, and `status`/`target`/`error` are a derived summary of it (`utils/importSession.ts:summarizeRegistrations`, always written through `withRegistration` so the two cannot drift). A single status could only describe one write, so pressing Group A left the Group B button dead until A settled, and "A failed but B succeeded" had no representation at all. Summary precedence is **queued > failed > duplicate > registered**: a row with anything in flight stays `queued` (hence `isLocked`, so its text can't be edited mid-write), and once everything settles a failure outweighs a success because that is the row the user still has to deal with. Everything downstream — `isLocked`, `sessionCounts`, the load-time reconciliation, the backend's `registeredCount` — still reads the summary and needed no change. Consequences: the entry guard refuses only `skipped` rows and a destination **already queued for itself**, and `DestinationButton`'s `disabled`/`busy`/`failed`/`error` all come from that destination's own slot (`disabled={stateA?.status === "queued"}`, not the row's). The piggyback guard likewise matches per destination. **Creates are serialized per term** by `createChain` (a `useRef` map of `kind term` → the in-flight create): two presses on a row whose entity does not exist yet would each call smart-add for the same term, and the server's duplicate check can pass both and store the word twice — so the second press awaits the first, re-reads the row, and finds the learned id, which turns it into the cheap group-add path. Group adds are set-based and idempotent, so they are never chained. The claim is released from `settle`, and the enqueue calls are wrapped in `try/catch → fail` because a throw there would leave the chain claimed and every later press for that term waiting forever. A row loaded still `queued` has its pending destinations settled by `load`'s `check-terms` reconciliation, or its button would spin (and stay disabled) for good.
    - **Registration records the real outcome.** `useImportSession.registerItem` enqueues ONE item and records it. Status is never inferred from `succeededTerms` — that set is term-keyed (so two rows sharing a term are indistinguishable), success-only, and in-memory. Instead both queue hooks gained an optional `onSettled` in their create options (`WordCreateOptions`/`GrammarCreateOptions`), invoked from the existing `.then`/`.catch`; the catch settles only after the draft-rescue resolves so `rescuedAsDraft` is accurate. **`onSettled`'s success payload carries the created entity's ID** (`wordId`/`grammarId`) — `processItem` already held it and used to throw it away, forcing the ID to be rediscovered through a debounced `check-terms`. On load, word rows still `queued` are reconciled against `checkTerms`; grammar has no existence check on the server, so those stay visibly unverified.
    - **Sibling propagation, and what is NOT propagated** (`useImportSession.applySettle`): an article repeats its vocabulary, so the entity ID a registration learns is knowledge about the TERM, not about that row. One `setItems` writes the outcome to the row and `existingWordId`/`existingGrammarId` to every live row sharing the trimmed term (word) or statement (grammar) — two `immediate` patches would each flush and cost a second PUT. Those siblings then render "already in your library" and their button takes the group-membership-only path. **Status is deliberately NOT propagated**: marking untouched rows `registered` would inflate the progress counter and `isLocked` them out of "Add to groups" after the destination changes. The lone exception is a row left `queued` by the **piggyback guard** — `registerItem` refuses to enqueue a second write for a term already in flight (the queue runs 4 at a time, so it would race, and at best return 409 with its group work skipped), and such a row has no write of its own to wait on, so it must inherit the leader's terminal status (including failure) or it spins forever.
    - **409 recovery.** A word 409 means the word IS in the DB but `smart-add` threw before the queue's group work, so nothing was written — and group membership was the whole point of the row. `registerItem` recovers the ID via `checkTerms`, applies `modifyGroupMembers` (set-based, so re-adding is a no-op) and settles as `registered`; only if recovery fails does it fall back to the neutral `duplicate`. Grammar needs no such branch — a grammar 409 is unreachable.
    - **Group membership is one read, shared** (`hooks/useImportGroups.ts`): the review screen used to fetch `getGroups` three times — the destination rail, the membership hook, and `GroupBUnifiedSelect` via `loadGroupBGroups` — for identical documents, and `WordGroup` already carries `wordIds`, so the membership data was on screen twice and discarded once. `useImportGroups` holds both collections with a debounced `reload()` (`getWordGroups` is O(library size) and registrations arrive in bursts), passed to `ImportDestinationRail` as props and to `useImportLibraryStatus`. The rail seeds `autoSelectLatest` **once per language** via a ref, so a post-registration reload cannot silently move the user's chosen destination.

Real group names distinguish "in the library" from "in the group this review is filling" — but `inLibrary` stays the fallback signal, because a term can be in the library and in no Group A group at all, and a word proven to exist by a 409 whose recovery failed has no ID to look names up by. `useImportSession.membershipOverlay` (`entityId → groupIds`, transient, cleared on session change) is **unioned** over the read to cover the gap between a write returning and the reload landing — it is not persisted on the items, since the server is the record and the reload answers the same question.
    - **Autosave**: debounced ~1.2s for free-text, flushed immediately for every status/destination change, on unmount and on `close()`. One PUT in flight at a time (`savingRef`/`pendingRef`), and only `updatedAt` is taken from the response — local state stays authoritative so edits made mid-request are not reverted. `resolveGroupBTargets` CREATES missing groups, so its result is memoized per domain per `groupBNames` rather than called per add.
