## Architecture

Full-stack vocabulary quiz app supporting four study languages (`en`/`ja`/`ko`/`zh`; HSK levels apply only to Chinese): **Fastify 5 backend** + **React 19 / Vite 6 frontend**.

### Backend (`backend/src/`)
- **Routes** (each is a `FastifyPluginAsync` registered under `/api`):
  - `routes/vocab.ts` — smart-add always asks LLM for all four codes (`en`/`ja`/`ko`/`zh`) — `ALL_DEFINITION_LANGUAGES` is hardcoded (lives in `exampleTranslations.ts` with `LANGUAGE_TO_ISO`); request body languages are anchors only. Empty example translations (chip adds send `""`) are normalized to `null` before the LLM call, and any example doc still empty after the merge is LLM-filled via `exampleTranslations.ts:generateMissingExampleTranslations` — shared by vocab POST/PUT and grammar's `resolveExamplesToIds`. Chinese levels normalized at storage time by `CHINESE_LEVEL_NORMALIZE`. Word-group ordering is persisted through `PUT /api/vocab/:language/groups/order`, whose `groupIds` body must contain every group for that language exactly once. **Word drafts**: `word_drafts` Firestore collection + CRUD under `/api/vocab/:language/drafts` (bulk POST assigns `id`/`createdAt` server-side; NO LLM at upload) — mirrors `grammar_drafts`. `WordList`'s "Upload JSON" button ingests `word-drafts` files (format: `docs/draft-json-format.md`). Draft examples may carry `segments: string[]` (chip segmentation — plain segment texts, NOT the `Example.segments` object shape); the review prefill re-inserts spaces at those boundaries (`spaceSentenceBySplits`) so the Chinese chip workflow picks them up and `buildPayload` re-emits them as smart-add `userSplits`. Review flow (mirrors grammar): drafts panel in `WordList` → `SmartAddWordModal` opens with `initialItem`/`initialGroups`/`draftId` prefill and TWO actions — "Save Draft" (form submit / Enter; `onDraftSave` → `PUT /drafts/:draftId`, writes edits back WITHOUT promoting) and an explicit "Register" button that ENQUEUES into the shared word queue (`enqueue` opts `{groupNames, draftId}`: worker creates missing draft groups under the module-level group lock and deletes the draft only after full success — a failed registration keeps the draft) and closes the modal immediately. In-flight drafts show a "Registering…" badge (via `pendingDraftIds`, threaded Dashboard → BrowseView → WordList) with Review/Discard hidden. **Drafts carry NO group data** (removed from the JSON format and both draft types): the drafts panel header has a group `<select>` — defaulting to the most recently CREATED group (`types.ts:latestWordGroup`, by `createdAt`; a user pick sticks until the language changes) — that supplies the target for both the per-row one-click "Register" button (`handleRegisterDraft` builds the smart-add payload straight from the draft, Chinese `segments` → `userSplits`, and enqueues with `{draftId}` so the queue deletes the draft only on full success) and the review modal's preselected group chip (`initialGroups`). A legacy `groups` field in an uploaded file or a direct POST is dropped. Fallback without `onQueue`: direct smart-add await where `onSave` (success-only) is the delete-draft signal.
  - `routes/quiz.ts` — `POST /start` accepts `groupWeights?: Record<string,number>` and `flaggedOnly?: boolean`. When `groupIds` are provided, questions are ordered by `weightedInterleave` (proportional to per-group weights, default 1) instead of `randomSample`; `randomSample` is still used for ungrouped sessions. Resume re-applies weights via `reweightUnanswered` (not a plain shuffle). `PUT /session/language/:language/weights` changes `groupWeights` MID-SESSION: it reorders the unanswered tail with the new weights and returns the full session (stored questions are hydrated) — `QuizTaking`'s "⚖ Adjust Weights" panel re-syncs its local order from the response and jumps to the first unanswered question. 2-step hydration: `POST /start` returns lightweight `{wordId, term}` only; client pages `GET /questions/:language?offset&limit` (`BATCH_SIZE=50` in `QuizTaking.tsx`) for `definitions`/`examples`/`hanjaReadings`. Wrong answers call `insertRetryQuestion` server-side, which splices the missed word back into `session.questions` and reshuffles the tail — `score.total` grows accordingly; the frontend re-renders from the mutated session.
  - `routes/grammar.ts` — `Grammar` has `statement` + `descriptions: Meaning[]` (mirrors `Word.definitions`). Examples are normalized into the shared `example_sentences` collection via `exampleIds[]` (mirrors `Word.exampleIds`); inline `Grammar.examples` is a transitional fallback for unmigrated docs. POST/smart-add/PUT resolve incoming `examples` to existing or new `example_sentences` docs via the sha256 dedup index (so a sentence shared with a vocab word gets one doc) and `addGrammar`/`updateGrammar` keep `ExampleSentence.appearsInGrammarIds` in lockstep using a Firestore batch. PUT delete-cascades dropped examples through `isExampleReferencedByAny` (cross-domain check covering both `Word.appearsInIds` and other `Grammar.exampleIds`). User-curated `grammar_groups` collection mirrors `word_groups` — per-language, owns membership via `grammarIds[]`. CRUD lives under `/api/grammar/:language/groups`. `POST /:language/smart-add` LLM-enriches `descriptions[].text` to all four ISO codes (mirrors vocab smart-add); `GrammarFormModal` create path uses smart-add, edit (PUT) stays manual. `GET/PUT /api/grammar/settings` persist `GrammarSettings { defaultDefinitionLanguage }` in Firestore doc `config/grammar_settings` — seeds the first description row in `GrammarFormModal` (module-level `cachedDefaultDescLang` avoids the fetch race on repeat opens). Grammar example translations pass through as-is (`string | Record<string,string>`): `hydrateGrammarItems` no longer coerces multi-lang objects to a single string; the UI renders them via `displayGrammarDefEntries`. Config in Firestore `config/grammar` (local source `backend/DB/grammer/config/`, pushed by `migrate-db-config-to-firestore.ts --prompts`). **Grammar drafts**: `grammar_drafts` Firestore collection + CRUD under `/api/grammar/:language/drafts` (bulk POST assigns `id`/`createdAt` server-side; NO LLM at upload). Drafts hold raw inline `examples` — never normalized to `example_sentences` until promoted. Sources: the local OCR tool (`~/workspace/textbook_content_extractor/server/`, separate repo, NOT deployed) posts directly, and `GrammarList`'s "Upload JSON" button ingests `grammar-drafts` files (format spec: `docs/draft-json-format.md`, which also pre-defines the future `word-drafts` format). Review flow: drafts panel in `GrammarList` → `GrammarFormModal` opens in create mode via its `initialItem` prop (prefill-only; `isEdit` stays keyed to `editItem`) with TWO actions: "Save Draft" (the form submit / Enter; `onDraftSave` prop → `PUT /drafts/:draftId`, writes edits back WITHOUT promoting — Chinese sentences keep user-typed spaces so chip splits survive the round-trip) and an explicit "Register" button that ENQUEUES into the shared grammar queue and closes the modal immediately so the next draft can be reviewed. `useGrammarQueue.enqueue` takes optional `{groupNames, draftId}`: the QUEUE worker attaches group names (created if missing, serialized via a module-level lock so parallel workers don't duplicate a new group) and deletes the draft only after full success — a failed registration keeps the draft. When a create has no `groupNames` (or `initialGroups`, on the non-queue fallback path), it defaults to the most recently created group for that language (`types.ts:latestGrammarGroup`, by `createdAt`) instead of staying ungrouped; a language with zero groups yet stays ungrouped. In-flight drafts show a "Registering…" badge (via `grammarPendingDraftIds` + legacy `grammarPendingTerms`, threaded Dashboard → BrowseView → GrammarList) with Review/Discard disabled. **Drafts carry NO group data** (mirrors words): the drafts panel header's group `<select>` (default = `latestGrammarGroup`, a user pick sticks until the language changes) feeds both the per-row one-click "Register" button (`handleRegisterDraft` → `onGrammarQueue(..., {groupNames, draftId})`, Chinese space-splits → `userSplits`) and the review modal's `initialGroups`. A legacy `groups` field in an uploaded file or a direct POST is dropped. Fallback without `onGrammarQueue`: direct smart-add await where `onSave` (success-only) is the delete-draft signal.
  - `routes/grammar-quiz.ts` — `/start` accepts `groupIds` to scope the pool (no chapters/subchapters/displayLanguage/quizMode). Questions are flashcard-style: `GrammarQuizQuestion` carries only `{grammarId, statement}` — the statement IS the prompt; the client fetches the full item (`GET /api/grammar/:language/items/:id`, hydrated examples included) and reveals descriptions + registered examples on answer. No LLM at question time. Also exposes `check-missing-words` and `add-missing-words` (currently unused by the UI after the quiz simplification).
  - `routes/import.ts` — `POST /api/import/:language/analyze-stream`, SSE-over-POST (same transport as `routes/translation.ts`). One FULL-model streaming call splits an article into paragraphs/sentences and extracts words + grammar points; `paragraphs` is the schema's first key so the client can live-render sentences from the partial stream (`api/import.ts:extractStreamingSentences`). Sentence indices are assigned SERVER-side by position (schema omits them, mirroring `ensureDecompositionIds`) and out-of-range extractions are dropped. Existing grammar `statement`s are injected as style examples. The server only analyzes + existence-checks (`lookupWordsByTerms`); **registration is entirely client-side** through the existing word/grammar queues, so there is no new write path. Grammar duplicates are NOT checked — imported grammar is always created fresh, by design. UI: `ImportView.tsx`, reached as the third tab of `BrowseView` (see below). **Import sessions**: the same file also serves CRUD for `import_sessions` under `/:language/sessions` (nested under `:language` to match the drafts convention and stay clear of `/:language/analyze-stream`) — `GET` (projected `ImportSessionSummary[]`, never the full items array), `POST` (201, server assigns `id`/`createdAt`/`updatedAt`), `GET/PUT/DELETE /:sessionId`. PUT is the autosave target and re-stamps `updatedAt`; `items` replaces wholesale so deleted/merged rows actually disappear. Collection schemas are loose (`items: {type:"array"}`) because a deep JSON schema fights the `ImportItem` discriminated union.
  - `routes/combined-quiz.ts` — merged word+grammar quiz at `/api/combined-quiz`. **UI naming**: surfaced to the user as "Group A Quiz" (paired with the Group B quiz); ALL code/route/i18n-key identifiers keep the `combined` name (`combinedQuiz`, `startCombinedQuiz`, `resumeCombinedQuiz`, `selectCombinedFilters`, route `/combined-quiz`) — only the displayed i18n string *values* were changed to "Group A". Two-level weighted ordering: each domain is ordered internally by group weights (`weightedInterleave`; grammar groups gain weights here — the standalone grammar quiz has none), then the two streams are merged by `domainWeights: {word, grammar}` via `weightedMerge` (order-preserving draw; a weight of 0 skips that domain). Questions are a `kind`-discriminated union (`CombinedQuizWordQuestion | CombinedQuizGrammarQuestion`); `/answer` takes `{kind, refId}` and dispatches to word vs grammar progress + retry re-queue. Word questions use the same 2-step hydration as `routes/quiz.ts` (`GET /questions/:language?offset&limit`); grammar questions are tiny (`{grammarId, statement}`, same flashcard format as the standalone grammar quiz) and stored inline — the client's grammar item-detail cache supplies descriptions/examples on reveal. Sessions live in `combined_quiz_sessions` keyed by language; resume (`GET /session/language/:language`) reweights the unanswered tail per-domain then re-merges (shared `reorderUnansweredTail` helper). `PUT /session/language/:language/weights` changes `domainWeights`/`wordGroupWeights`/`grammarGroupWeights` MID-SESSION via the same helper and returns the full session — `CombinedQuizTaking`'s "⚖ Adjust Weights" panel re-syncs from the response; at least one domain weight must stay positive (a 0-weight domain's remaining questions are appended at the end, not dropped). Shared ordering helpers (`shuffle`/`weightedInterleave`/`weightedMerge`/`insertRetryQuestion`) live in `src/quiz-utils.ts`, also used by `routes/quiz.ts`. **Group B quiz**: the plugin is a factory `makeCombinedQuizRoutes({ sessionKey })` registered TWICE — `/api/combined-quiz` (key = `language`) and `/api/group-b-quiz` (key = `` `${language}__groupB` ``), so both sessions coexist in `combined_quiz_sessions` for one language. `getCombinedQuizSession` takes the doc key (not the language) and `saveCombinedQuizSession` keys off `session.sessionId`; `session.language` stays the plain language for client API calls. The B variant sends no `flaggedOnly`, and its pool is scoped purely by the category-B `groupIds` the client sends. Frontend: `api/combined-quiz.ts` takes a `variant?: "combined" | "groupB"` on all five functions; `CombinedQuizFilterModal` takes `groupCategory`/`showFlaggedToggle`; `CombinedQuizTaking` takes `variant`, where the "3" key becomes "remove from all Group B groups" for BOTH kinds (local badge only — the item stays in the running session).
  - `routes/expressions.ts` — CRUD + group management for `Expression` items at `/api/expressions/:language`. No LLM; fully user-curated. Mirrors grammar pattern (`expression_items`/`expression_groups` collections).
  - `routes/expression-quiz.ts` — Expression quiz **embedded as a subsession** inside `SpeakingWritingSession` (`SpeakingWritingSession.expressionQuiz?: ExpressionQuizSubsession`). Uses the same S&W correction LLM config; appends phrase/context to the base system prompt. Routes: `POST /start`, `POST /answer`, `POST /grade`, `GET /session/language/:language`.
  - `routes/translation.ts` / `routes/speaking-writing.ts` — SSE streaming via POST endpoint
  - `routes/translation.ts` — `language` prop = **target** language (active study language); user selects source. Two-step: decompose (MINI, source-lang prompt) → translate (FULL, target-lang prompt). Output uses `passages[].{ sentenceIds[], translation }` — LLM may group consecutive sentences. `buildTranslateSystemPrompt` appends source/target + approach guidance + optional user `context` (situation/register hint, persisted on `TranslationEntry.context`) to the Firestore prompt without needing a migration — context must stay LAST so the static prefix keeps hitting OpenAI prompt caching. The decompose schema omits sentence/chunk/component IDs; `ensureDecompositionIds` assigns them positionally server-side (tolerates old ID-carrying outputs). `/translate-stream` accepts an optional `decomposition` body field — the client (`TranslationView`) replays the previous `decompose-result` on regenerate for unchanged text+source so step 1 is skipped. `TranslationView`'s loading phase live-renders passages from the partial stream via `extractStreamingPassages` (passages are the first key in the translate response).
- **Database**: `firestore.ts` — `updateWord` per-sentence-merges old example `segments` onto incoming `examples` when sentence text is unchanged, so `WordFormModal` (which doesn't carry segments through form state) doesn't wipe LLM-generated pinyin on save. `getCanonicalSegmentPinyin(word)` returns `undefined` for polyphonic words so callers keep the LLM-generated contextual value. `getNextWordId` and `getNextExampleId` use Firestore transactions (not get-then-increment) to prevent duplicate IDs under the `CONCURRENCY=4` parallel smart-add queue — duplicate IDs cause one word to clobber another's doc and leave a ghost `word_index` entry. `checkTerms` validates `word_index` entries via `wordEntryIsLive` to filter out orphaned/mislinked entries before reporting a word as "existing".
- **LLM**: `llm.ts` — `callLLM*` functions use the MINI OpenAI model; `callLLMFull*` use the FULL OpenAI model. Config from `.env` (local) or Firestore `config/llm` (deployed).
- **Types**: `types.ts` — `Word` carries optional `hanjaReadings?: HanjaReading[]` (`{ simplifiedChar, traditionalChar, hunEum[] }` per character)
- **Type mirroring**: `backend/src/types.ts` and `frontend/src/types.ts` share translation interfaces (`TranslationResult`, `TranslationPassage`, `TranslationEntry`), grammar/example shapes (`Grammar`, `GrammarExample`, `ExampleSentence`, `GrammarSettings`), expression shapes (`Expression`, `ExpressionGroup`, `ExpressionQuizSubsession`), AND combined-quiz shapes (`CombinedQuizQuestion`, `CombinedQuizSession`, `CombinedDomainWeights`) — update both files together.
- **`userSplits` contract**: Chinese examples in both `WordFormModal` and `GrammarFormModal` strip `[\s　]+` from the sentence on save and attach `userSplits: string[]` (the segment texts). Backend routes (`vocab.ts`, `grammar.ts:resolveExamplesToIds`) feed `userSplits` to `fillSegmentPinyin` + `lookupWordsByTerms` to produce `example_sentences.segments` with word IDs. `GrammarExample.userSplits` is input-only — never persisted.

### Data Storage
- **Firestore** (database ID: `vocab-database`). Key composite keys: `progress`/`word_index` use `{language}_{wordId}`, `example_sentence_index` uses `{language}_{sha256(sentence).slice(0,16)}`.
- `example_sentences` — normalized; words store `exampleIds` and `appearsInIds` arrays referencing this collection. **Grammar items also reference this collection** via `grammar_items.exampleIds[]`; the reverse link is `ExampleSentence.appearsInGrammarIds[]`. A sentence shared by a word and a grammar item resolves to ONE doc via the sha256 dedup index. Orphan deletion (in `deleteWord`, `deleteGrammarItem`, and the vocab/grammar PUT routes) MUST use `isExampleReferencedByAny` so vocab deletes don't clobber grammar-owned examples (and vice versa). `validate-invariant-all.ts` enforces the bidirectional invariant `ES.appearsInGrammarIds == { gId | grammar(gId).exampleIds ∋ ES.id }`.
- `config` subcollections: `config/llm`, `config/token_costs`, `config/speaking_writing`, `config/translation`, `config/vocabulary`, `config/grammar`, `config/grammar_settings`, `config/import`
  - `config/import` fields: `analyzeSchema`, `analyzePrompts` (keyed by backend language NAME) — local source in `backend/DB/import/`; push with `migrate-db-config-to-firestore.ts --prompts`. `routes/import.ts` loads it LAZILY so a missing doc can't stop the server from booting.
  - `config/translation` fields: `decomposeSchema`, `decomposePrompts`, `translateSchema`, `translatePrompts` — local source in `backend/DB/translation/`; push with `migrate-db-config-to-firestore.ts --prompts`
- `import_sessions` — one paused, resumable article review each (auto-ID docs with a `language` field, listed by an in-memory `updatedAt` sort to avoid a composite index — the `translation_history` pattern, NOT the singleton-per-language quiz/speaking pattern, since several articles can be in progress at once). Holds `paragraphs` + the flattened `items` working copy + destination groups; see the `ImportView.tsx` entry below for the item model.
- `expression_items`, `expression_groups` — per-language, mirror the grammar collection structure. `ExpressionQuizSubsession` is NOT a separate collection; it is stored as `SpeakingWritingSession.expressionQuiz?` in `speaking_writing_sessions`.
- **Meta-groups (`category`)**: `word_groups`/`grammar_groups` docs carry an optional `category?: "A" | "B"`. **Absent = "A"** and only `"B"` is ever written, so every pre-existing group is Group A with zero migration. "A" is the universe of all items (every existing flow — drafts, chips, browse filters, word/grammar/combined quiz setup — filters to A via `types.ts:categoryGroups`); "B" is the not-yet-memorized subset drilled by the Group B quiz. `latestWordGroup`/`latestGrammarGroup` reduce over category A only, so a B group is never an implicit default. Group B membership is added on top of A by the shared `GroupBSelect.tsx` chips (every add flow assigns an A group, which is what upholds "a B item is always also in A" — there is NO server-side validation). **A Group B group spans both domains**: unlike Group A, where a word group and a grammar group are unrelated sets, one Group B study set holds words AND grammar. It is still stored as two docs (one `word_groups`, one `grammar_groups`, both `category: "B"`) joined by NAME — `frontend/src/utils/groupB.ts` (`UnifiedGroupB`, `loadGroupBGroups`, `createGroupBGroup`, `resolveGroupBTargets`) is the merge/create/resolve layer, and `GroupBUnifiedSelect.tsx` is the name-keyed picker built on it (with inline "new group" creation, which creates both sides at once). `resolveGroupBTargets` only materializes the side a registration actually needs, so importing an article with no grammar never leaves an empty grammar group behind. The per-domain `GroupBSelect.tsx` stays in use by the single-domain add forms. Category is fixed at creation (no PUT). `firestore.ts:removeWordFromCategoryBGroups` / `removeGrammarFromCategoryBGroups` back `DELETE /:language/group-b/members/:id` on both vocab and grammar. **Reorder invariant**: `PUT /vocab/:language/groups/order` still requires EVERY group of the language exactly once, so `GroupPickerModal` appends the hidden category's IDs after the visible reordered ones.
- `word_groups` — per-language groups own membership through `wordIds[]` and may carry numeric `order`. `getWordGroups` sorts by `order`, with creation time as the legacy fallback. The first reorder operation backfills a complete zero-based order for all groups; new groups append to an ordered list.
- **Local files**: `backend/DB/` (grammer, speaking&writing, translation, vocabulary, backup, old, original). Word JSON is no longer mirrored locally — Firestore is the source of truth; `old/` and `original/` hold pre-migration HSK archives.

### Language Code Convention
All language codes use ISO 639-1: `ja`, `en`, `ko`, `zh`. The export script normalizes legacy keys (e.g., `"Japanese"` → `"ja"`, `"kr"` → `"ko"`) on export.

### Frontend (`frontend/src/`)
- **Settings**: `settings/context.tsx` — persisted to `localStorage("appSettings")`.
  - `defaultAddWordLanguage` — backend full-name format (`"english"`, `"chinese"`) — **different from** `defaultDefinitionLanguage` (ISO code)
  - `showKoreanHanja` — only shown in Settings when active language is Chinese
  - `displayGrammarDefinitionLanguages` — filters grammar description/example-translation languages via the `displayGrammarDefEntries` helper (grammar's own default definition language is server-side: `config/grammar_settings`, not localStorage)
- **API layer**: `api/client.ts` — non-ok responses include body text in thrown error
- **i18n in sub-components**: Module-level React components (outside `TranslationView`) must explicitly call `const { t } = useI18n()` — they don't inherit it from parent scope.
- **Key components**:
  - `SmartAddWordModal.tsx` — **two independent language fields**: outer "word language" (backend full-name) vs. per-row "definition language" (ISO code). Queue mode (`onQueue` prop): Submit enqueues immediately and resets form.
  - `WordFormModal.tsx` — does not carry `segments` through form state (preserved server-side by `firestore.ts:updateWord`)
  - `GroupPickerModal.tsx` — shared word/grammar group picker and manager. In word-group management mode (`itemIds.length === 0`), rows use `@dnd-kit` drag handles and persist reordering immediately through `reorderGroups`; grammar groups are not reorderable. `onDone` synchronizes parent group state but does not imply closing the modal—add flows call `onClose` themselves.
  - `ExampleSentenceEditor.tsx` — shared example-sentence editor used by `WordFormModal` AND `GrammarFormModal`. Owns the Chinese segment-chip "+" workflow — direct mode calls `smartAddWord`; queue mode (`onQueue`) enqueues into the shared word queue. The chip rendering + space-splitting + `userSplits` payload are all gated by literal `language === "chinese"` (backend full-name, NOT ISO `"zh"`). Pass the active language string straight through — any sentinel (e.g. `"open"`) silently disables the workflow. **Chip status invariant** (shared with `SmartAddWordModal.tsx`): 3 states — green ✓ = `existingTerms ∪ succeededTerms ∪ addedTerms`, amber ⋯ = `pendingTerms`/`busySegments`/`checkingTerms`, blue + otherwise. Green MUST come from the queue's `succeededTerms` (passed down beside `pendingTerms`), NOT the wholesale-replaced `checkTerms` poll — that poll only detects pre-existing words and is too racy under `CONCURRENCY=4` to signal completion.
  - `constants/levels.ts` — `LEVEL_OPTIONS` (HSK/JLPT buckets). Used by `SmartAddWordModal` and `GrammarFormModal`. Backend keeps its own copy in `routes/vocab.ts` (LLM-output normalization concern).
  - **Queue `onSettled`**: both `useWordQueue` and `useGrammarQueue` create-options accept an optional `onSettled(result)` giving the outcome of ONE enqueued item (`{ok:true}` or `{ok:false, error, duplicate, rescuedAsDraft}`). Added for the article importer, which must report per-item fate; it is held in queue state only and never serialized, so every other caller is unaffected.
  - `hooks/useWordQueue.ts` — runs `CONCURRENCY=4` items in parallel (NOT one-at-a-time). Supports two item types: `create` (via `enqueue(term, language, payload, opts?)` — opts `{groupNames?, draftId?}` mirror `useGrammarQueue`: group names are created if missing under a module-level lock, the source draft is deleted only after full success) and `update` (via `enqueueUpdate(term, language, wordId, updates, groupsToAdd, groupsToRemove)`). Exposes `pendingTerms` (queued+processing), `succeededTerms` (cumulative, monotonic set of finished adds) — the authoritative signals segment chips use for status — and `pendingDraftIds` (drives the drafts panel's "Registering…" badge). Also bumps `refreshSignal`. **Failure rescue** (both this hook and `useGrammarQueue`): a failed `create` with no `draftId` is saved as a word/grammar draft so the input isn't lost (segment-chip adds have no other record) — skipped for 409 duplicates; chip splits survive as draft `segments` (word) / re-inserted spaces (grammar), but the group target does NOT (drafts hold no groups; it is re-picked at registration). Draft-originated failures need no rescue: their draft still exists.

  - `ImportView.tsx` — a thin phase router (`sessions` → `input` → `analyzing` → `review`); everything else lives under `components/import/` plus `hooks/useImportSession.ts` and `utils/importSession.ts`. Destination is picked before analysis and stays editable through review (`ImportDestinationRail`: two **Group A** selects defaulting to `latestWordGroup`/`latestGrammarGroup`, plus a **Group B** `GroupBUnifiedSelect`); it applies to items added *from then on*, not retroactively.
    - **Item model** (`utils/importSession.ts`, all pure): the analysis's positional `words[]`/`grammar[]` are flattened once into `ImportItem[]` with stable client ids — the raw arrays are NOT persisted, so there is one working copy and no drift. `order` is **fractional** so a split inserts its parts between neighbours without renumbering. Merge/split/delete **tombstone** their sources (`status:"skipped"` + `supersededByIds`) rather than removing them, which is what makes `undoDerivation` possible and keeps the session a complete record. `mergeWordItems` derives the new term from the sentence SPAN the sources cover (`sentenceSpanForTerms`), not naive concatenation, falling back to concatenation when a term isn't a literal substring; it keeps `transliteration` only if every source had one and always drops `meaning` (a compound's gloss is not the sum of its parts).

Prev/next and click-to-jump move focus.
    - **Mobile layout (`ImportReview` + `ImportSentenceCard`)**: the review screen is mobile-first and must NOT scroll horizontally — it used to overflow its scrollport by ~257px at 360px wide. Four rules hold that: (1) the scroll container carries `overflow-x-hidden` as a hard stop, and `StatusChip` is `max-w-full truncate` because a long grammar `statement` is otherwise an unbreakable flex item; (2) **every text input/select/textarea in the importer is `text-base` (16px) below `sm`** — anything smaller makes iOS zoom the viewport on focus, which reads to the user as horizontal scrolling (same `text-base … sm:text-xs` pattern as `GroupBUnifiedSelect`); (3) `WordRow`/`GrammarRow` stack term-over-reading with the actions on a second line below `sm` and collapse back to the original single row from `sm`, and the paragraph-number gutter moves above the paragraph below `sm` (~50px of text width recovered); (4) collapsed sentences are `line-clamp-2 sm:line-clamp-1` — one ellipsized line is too little to pick the next sentence from. `ImportDestinationRail` takes `collapsible`: below `lg` it renders as a disclosure (one-line summary of the chosen groups) placed via `lg:col-start-2 lg:row-start-1` FIRST in DOM so it leads on a phone and is still the sticky right sidebar from `lg`; prev/next is a `sticky bottom-0 … lg:hidden` bar (the inline nav is `hidden lg:flex`), with `scroll-mb-24` on the focused card so `scrollIntoView` clears it.
    - **Registration is per item.** `useImportSession.registerItem` enqueues ONE item and records the real outcome. Status is never inferred from `succeededTerms` — that set is term-keyed (so two rows sharing a term are indistinguishable), success-only, and in-memory. Instead both queue hooks gained an optional `onSettled` in their create options (`WordCreateOptions`/`GrammarCreateOptions`), invoked from the existing `.then`/`.catch`; the catch settles only after the draft-rescue resolves so `rescuedAsDraft` is accurate. `duplicate` (409) is rendered as a neutral "already in library", NOT a green ✓, because the queue's group work never ran. On load, word rows still `queued` are reconciled against `checkTerms`; grammar has no existence check by design, so those stay visibly unverified.
    - **Autosave**: debounced ~1.2s for free-text, flushed immediately for every status/destination change, on unmount and on `close()`. One PUT in flight at a time (`savingRef`/`pendingRef`), and only `updatedAt` is taken from the response — local state stays authoritative so edits made mid-request are not reverted. `resolveGroupBTargets` CREATES missing groups, so its result is memoized per domain per `groupBNames` rather than called per add.
